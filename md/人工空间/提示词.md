# 自迭代

自迭代测试流程 · 搭建指令

你的任务
为当前项目搭建一套"自迭代体验优化"流程文档和结构。只搭流程，不做项目功能。

核心需求
项目每次完成一个大版本后，必须自动执行一轮"玩家/用户视角"的体验验证，通过后才进入下一版本。整个循环（开发→验证→修复→下一版本）应能无人值守地持续运行。

要求

测试原则
以操作日志为主要测试依据（操作类型、时间戳、响应延迟、是否达成预期），截图仅作辅助（每轮≤3张），禁止录视频
模拟一个"第一次使用、毫无经验的普通用户"，关注：操作是否多余、反馈是否及时、界面是否看得清看得懂、是否知道下一步该干嘛
按项目平台，选择合适的基准分辨率
测试必须高效：一轮验证控制在合理时间内，不频繁触发，只在大版本节点执行

体验底线（写进流程文档）
一次点击能完成的事不拆两步；可撤销操作免确认
任何交互 100ms 内必须有反馈；无反馈即视为缺陷
用户任何时刻都能知道"下一步干什么"
误操作有柔和提示，不出现无反应或报错弹窗
字号、热区、对比度满足基本可读性
同类操作全局一致

产物管理
测试产物（日志、截图）只保留最近一轮，旧的在每轮开始前清理
清理范围严格限定在项目测试产物目录内，禁止触碰项目源码、系统文件、其他项目
只维持一个 latest build

记忆与上下文
上下文会被压缩，会话需长期运行。设计一个轻量的记忆机制（如项目根目录下一个简短的状态文件），记录：当前版本号、上轮自审结论、未解决问题、下一步目标
记忆文件保持精简，不要膨胀

项目结构
整体结构保持简单清晰，不要为了流程引入复杂目录
流程文档用简洁明了的 md 写，AI 后续每次执行时读取即可

注意
以上仅为需求和方向，具体实现方式（脚本选型、日志格式、目录结构、清理策略）由你根据项目实际情况自行决定
不要过度设计，够用、能跑、高效即可
搭完后简要说明你做了什么、结构是什么，不需要长篇解释
