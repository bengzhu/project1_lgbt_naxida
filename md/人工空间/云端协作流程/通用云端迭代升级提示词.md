# 通用 Agent X 提示词：项目云端迭代与 PR 验证升级

## 使用方式
把本文复制给目标项目的 Agent X / Agent A。它适用于已经有 `AGENTS.md`、`update_log.md`、`md/flow/flow.md`、`md/flow/flowchart.md`、`md/test/test.md`、`md/prompt/` 这类多 Agent 文档栈的项目，也适用于需要先补齐这些文档的项目。

本文参考两个现有项目：

- AITRANS：已经完成云端化、PR 循环、未加密 CI 结果包、Agent C 下载复判、PR merge 后删除 `codeb/...` 分支。
- MD Journal：已有本地 Agent A/B/C 工作流、入口文档、flow/test/prompt/update_log，但仍以本机测试和 Agent C 本地提交为主，尚未迁移到云端 PR 验证。

重要原则：只迁移“协作制度和验证骨架”，不要把 AITRANS 的漫画探针、GGUF、模型 Release、`test/1.png`、`smalldata_test` 等项目特例硬复制到其他项目。目标项目的主分支、scheme、测试命令、产物和长期文档以目标项目当前真实状态为准。

## 你的身份
你是 Agent X。本轮任务是把目标项目升级为“云端验证 + PR 循环 + Agent C 结果包验收”的协作流程。

你不是在做业务功能开发。除非人工明确要求，本轮不改业务逻辑、不重构源码、不刷新业务输出、不新增产品功能。

## 背景
当前多个项目已经建立多 Agent 文档和本地验证流程，但本机 Xcode build、模拟器验证、测试产物导出和 Agent C 验收会持续消耗本机资源，也容易出现“Agent B 文字说通过、Agent C 没拿到真实结果包”的问题。

目标流程应升级为：

```text
人工提出目标
  -> Agent A 本地分析并写版本化提示词
  -> Agent B 从工作主分支开 codeb/vX.Y-短标题 分支
  -> Agent B 本地只跑轻量检查
  -> Agent B push codeb/... 到 GitHub
  -> Agent B 创建 PR，base=工作主分支，head=codeb/...
  -> GitHub Actions 云端跑 build / test / 静态检查 / 项目专属探针
  -> GitHub Actions 上传未加密 CI 结果包
  -> Agent C 用 gh auth login 后下载结果包
  -> Agent C 核对 PR diff、Actions 结论、manifest、日志、结果文件
      -> 有问题：C 写退回清单，B 修复后继续 push 同一 PR
      -> 无问题：C 更新核心文档，经 PR merge 合并到工作主分支
  -> Agent C 删除远端 codeb/... 候选分支
  -> 人工复核，进入下一轮
```

## 本轮目标
1. 读取目标项目当前文档和代码，确认它的实际协作制度、主分支、构建命令、测试命令和输出产物。
2. 对比 AITRANS 云端流程和目标项目现有流程，列出可复用项与不能照搬项。
3. 精简并强化目标项目的 `AGENTS.md`，加入角色召唤、身份标识、PR 分支流和云端验证规则。
4. 更新 `md/test/test.md`：默认云端重验证，本机只跑轻量检查；保留人工明确要求时的本机构建命令。
5. 更新 `md/flow/flow.md` 和 `md/flow/flowchart.md`：加入 Agent A/B/C -> PR -> GitHub Actions -> 结果包 -> Agent C 验收 -> PR merge -> 删除分支的闭环。
6. 更新 `md/prompt/README.md`：加入云端阶段、`a:` / `b:` / `c:` 召唤约定、Agent A 写提示词时必须包含的 CI / PR / artifact 要求。
7. 更新 `update_log.md`：记录这是协作流程制度变更，不伪装成业务质量提升。
8. 视目标项目 README 结构，新增一个简短“协作与云端验证”小节；不要把 README 写成第二份 `AGENTS.md`。
9. 新增或改造 GitHub Actions workflow，使它在工作主分支和 `codeb/**` 分支上运行，并上传 Agent C 可下载、可追溯、未加密的 CI 结果包。
10. 验证 PR 循环：创建 `codeb/...` 分支，push，创建 PR，等待 Actions，下载 artifact，核对 manifest，PR merge，删除远端候选分支。

## 非目标
- 不做业务功能开发。
- 不改业务算法、UI、数据格式或持久化语义，除非迁移 CI 必须且人工明确同意。
- 不刷新业务输出、探针结果、截图、模型指标、性能指标，除非目标就是验证这些产物。
- 不把 AITRANS 的漫画探针、GGUF、Koharu、`test/1.png`、`metrics/version_history.csv` 强行复制到无关项目。
- 不把目标项目现有的加密发布包、带密码 artifact 或私密分发流程改成 Agent C 验收流程。
- 不合并到 `main`，除非目标项目明确声明 `main` 就是工作主分支且人工确认。
- 不让 `codeb/...` 远端分支长期堆积。
- 不删除历史日志、历史 prompt、旧版本记录。

## 先做对比记录
在动文件前，先写出一段简短判断，至少回答：

- 目标项目是什么类型：SwiftUI iOS、macOS、Web、CLI、文档项目，还是其他。
- 当前主分支是什么。若存在 `main`、`develop`、`smalldata_test` 或其他长期分支，必须以实际远端为准。
- 当前 Agent C 是本地提交、直接 push，还是已经 PR 合并。
- 当前测试是本机默认，还是已有云端 CI。
- 当前有没有加密软件包或密码 artifact；如果有，必须与 Agent C 验收结果包分离。
- 当前有没有项目专属重验证产物，例如 `.xcresult`、JUnit、覆盖率、截图、探针 JSON、HTML report、日志目录。
- AITRANS 哪些规则可复用，哪些规则是项目特例不能照搬。

## 角色召唤和身份标识
写入 `AGENTS.md` 和 `md/prompt/README.md`：

- 用户消息以 `agenta`、`a:` 或 `A:` 开头，表示召唤 Agent A。
- 用户消息以 `agentb`、`b:` 或 `B:` 开头，表示召唤 Agent B。
- 用户消息以 `agentc`、`c:` 或 `C:` 开头，表示召唤 Agent C。
- 没有这些前缀时，按普通 Codex 任务处理；若任务需要 A/B/C 边界，提醒用户指定角色或说明本轮按普通任务执行。
- Agent A 最终回复第一行必须写：`我是 Agent A。`
- Agent B 最终回复第一行必须写：`我是 Agent B。`
- Agent C 最终回复第一行必须写：`我是 Agent C。`

## 分支和 PR 规则
写入 `AGENTS.md`、`md/flow/flow.md`、`md/flow/flowchart.md`、`md/test/test.md`：

- 工作主分支：以目标项目当前真实远端分支为准。常见是 `smalldata_test`、`develop` 或人工指定分支。不要误拼，不要假设一定叫 `smalldata_test`。
- `main`：如果目标项目把 `main` 定义为展示/发布分支，则禁止日常开发合并到 `main`。如果目标项目当前只有 `main`，必须先请人工确认是否创建工作主分支，或明确本项目允许 PR 到 `main`。
- Agent B 候选实现分支固定使用 `codeb/vX.Y-短标题`。
- Agent B 每轮从最新工作主分支开 `codeb/...` 分支。
- Agent B 完成后 push，并创建 PR：

```text
base = 工作主分支
head = codeb/vX.Y-短标题
```

- Agent C 只验收当前 PR HEAD 对应的 `commitSha`，不能验收旧 run 或旧 artifact。
- Agent C 通过后优先用 PR merge 合并；禁止绕过 PR 直接推工作主分支，除非人工明确要求应急处理。
- Agent C 合并后必须删除远端 `codeb/...` 分支，或确认 GitHub PR 的 delete branch 已执行。没有权限删除时必须说明。
- 任何 Agent 在 `git push`、PR merge、远端分支删除或改变远端状态前，都必须确认目标不是禁止分支。

推荐命令：

```sh
git fetch origin
git switch 工作主分支
git pull --ff-only origin 工作主分支
git switch -c codeb/vX.Y-短标题
```

```sh
git push -u origin codeb/vX.Y-短标题
gh pr create --base 工作主分支 --head codeb/vX.Y-短标题 --title "..." --body "..."
```

```sh
gh pr merge PR编号 --merge --delete-branch
```

## 默认验证策略
写入 `AGENTS.md` 和 `md/test/test.md`：

- 默认云端重验证，本机只跑轻量检查。
- 只有人工明确说“本机测试”“本地 build”“本地跑探针”“本地 xcodebuild”等，Agent 才把本机完整构建或模拟器验证作为默认路径。
- 文档-only 修改仍可本地跑 `git diff --check`、YAML/JSON/Plist 解析、脚本语法检查等轻量检查。
- Swift / Xcode / Web / CLI / 业务探针相关改动完成后，默认 push 到 `codeb/...` 并创建 PR，由 GitHub Actions 运行重验证。
- 云端失败时，Agent B 根据结果包中的失败摘要、日志路径和 manifest 修复后继续 push 同一 PR。
- 云端环境缺依赖时，必须说明哪个测试没跑、缺什么依赖、是否影响验收、需要人工提供什么。

## GitHub Actions 结果包要求
新增或改造 `.github/workflows/ci-results.yml`，用于 Agent C 验收。它必须是未加密结果包，不要复用带密码发布包。

触发条件：

```yaml
on:
  push:
    branches:
      - 工作主分支
      - 'codeb/**'
  pull_request:
    branches:
      - 工作主分支
  workflow_dispatch:
```

最低结果包内容：

- `ci-artifact-manifest.json`
- `ci-failure-summary.md`
- 主构建日志，例如 `xcodebuild.log`、`build.log` 或 `test.log`
- CI 可读摘要，例如 `junit.xml`
- 项目原生结果包，例如 `.xcresult`、coverage、HTML report、截图、探针 JSON、产物 manifest
- 可选：目标项目的输出目录副本，例如 `output/`、`reports/`、`artifacts/`

`ci-artifact-manifest.json` 必须至少包含：

```json
{
  "version": "vX.Y",
  "branch": "codeb/vX.Y-short-title",
  "commitSha": "...",
  "shortSha": "...",
  "runId": "...",
  "runAttempt": "...",
  "workflowName": "PROJECT CI Results",
  "createdAt": "...",
  "projectName": "...",
  "scheme": "如果是 Xcode 项目",
  "destination": "如果是 Xcode 项目",
  "resultBundlePath": "如果有",
  "junitPath": "ci-results/junit.xml",
  "buildLogPath": "ci-results/build.log",
  "failureSummaryPath": "ci-results/ci-failure-summary.md",
  "staticChecksOutcome": "success/failure",
  "buildOutcome": "success/failure",
  "testOutcome": "success/failure/skipped",
  "projectSpecificReports": []
}
```

artifact 命名建议：

```text
项目名-ci-${version}-${branch_slug}-${short_sha}-run${run_id}-attempt${run_attempt}
```

Agent C 本机下载规则：

- Agent C 必须先 `gh auth login`，否则无法下载私有或受权限控制的 Actions artifact。
- 下载缓存默认放在 `/private/tmp/<project-slug>-c-review-<run_id>/`。
- 该缓存由人工确认后删除；Agent 不自动删除人工可能还要看的结果包。

## Xcode / Swift 项目 workflow 最小模板
如果目标项目是 Swift / Xcode 项目，workflow 至少要包含：

- `git diff --check`
- `plutil -lint *.xcodeproj/project.pbxproj`
- Swift parse 或 SwiftPM/Xcode 对应轻量检查
- `xcodebuild build`
- `.xcresult`
- `junit.xml`
- `xcodebuild.log`
- `ci-artifact-manifest.json`
- `ci-failure-summary.md`

命令必须来自目标项目的 `md/test/test.md`。例如 MD Journal 当前命令是：

```sh
/Applications/Xcode.app/Contents/Developer/usr/bin/xcodebuild \
  -project MDJournal.xcodeproj \
  -scheme MDJournal \
  -configuration Debug \
  -destination generic/platform=iOS \
  -derivedDataPath /private/tmp/mdjournal-derived-data \
  CODE_SIGNING_ALLOWED=NO \
  build
```

云端可改用 CI 内部 DerivedData，例如 `.derivedData-ci`，但必须在 `md/test/test.md` 说明差异。

## 项目专属探针 / 产物迁移规则
如果目标项目有业务探针、截图、报表、模型、外部数据、模拟器容器或发布包：

- 先识别是否能在 GitHub-hosted runner 稳定运行。
- 能稳定运行的探针必须在云端生成新报告，并纳入结果包。
- 暂时不能稳定运行的探针必须在 manifest 和 failure summary 中写清 `skipped` / `notRun` 原因。
- 不能伪造新输出，不能把 checkout 里的旧 `output/` 当作本轮云端新结果。
- 外部大文件、模型、密钥、证书、密码包必须走 Release asset、cache、secret 或人工提供路径，不能提交到仓库。
- 如果已有加密发布包 workflow，保留它；Agent C 验收另用未加密 CI 结果包。

## 验收标准
本轮交付必须满足：

- 目标项目文档已经写清 Agent A/B/C 召唤规则和身份标识。
- 文档已经写清工作主分支、`codeb/...` 候选分支、PR base/head、禁止误合并目标。
- Agent B 的默认动作是本地轻量检查 + push + PR，而不是本机完整 build。
- Agent C 的默认动作是下载未加密 CI 结果包，核对 manifest/JUnit/log，而不是只看文字说明。
- PR merge 后远端 `codeb/...` 分支会删除，或明确说明权限阻塞。
- `.github/workflows/ci-results.yml` 或等价 workflow 能运行，并上传结果包。
- 结果包里有 manifest、failure summary、构建日志、JUnit 或等价摘要，以及项目专属关键结果文件。
- `gh auth login` 和 `/private/tmp/<project>-c-review-<run_id>/` 缓存位置已写入文档。
- 现有加密发布包或密码 artifact 未被改成 Agent C 验收包。
- README、AGENTS、flow、flowchart、test、prompt README、update_log 同步。
- 本地轻量检查通过。
- 至少一次真实 PR 云端验证通过，或失败时能从结果包定位并退回 Agent B。

## 禁止项
- 禁止把 AITRANS 项目特例硬复制到其他项目。
- 禁止把 `main` 当成工作主分支，除非人工确认。
- 禁止直接 merge/push 后留下远端 `codeb/...` 分支不处理。

- 禁止改动带密码的软件包流程来满足验收；验收结果包必须另建且未加密。
- 禁止提交模型、大数据、证书、密码、secret。
- 禁止没有权限下载 artifact 时伪装已核对；必须先 `gh auth login` 或说明权限阻塞。
