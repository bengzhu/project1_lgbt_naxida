# AITRANS v1.38 与 Koharu 当前差距研究

日期：2026-07-02
目标：基于 AITRANS 当前代码、流程文档、更新记录、本地 `output/` 和 `reference/koharu-main` 源码，判断当前链路距离 Koharu 还有多少差距，以及下一步算法应该往哪里靠。

## 结论

AITRANS 现在已经把 Koharu 的阶段名、artifact 依赖、gate ledger 和 report-only 审计框架基本搭出来了，但离 Koharu 的真实效果仍有明显距离。核心差距不是“报告字段不够”，而是 Koharu 的 TextBoxes、SegmentMask、BubbleMask、RenderedSprites 都是真实下游消费的中间产物；AITRANS 目前多数对应物还是 Vision OCR / 几何 proxy / shadow report。

按工程阶段估算：

- 诊断和可解释性：约 `70%` 接近 Koharu。当前已经能解释 TextBox、BubbleMask、SegmentMask、BubbleIndex、DistanceField、RenderSprite 等阶段缺口。
- 主 OCR / 结构化检测：约 `30%` 接近 Koharu。当前仍以 Apple Vision whole-page OCR 和 bubble-first 融合为主，没有真实文本检测模型和 line polygon。
- BubbleMask / SegmentMask：约 `25%` 接近 Koharu。AITRANS 有 rounded-rect / glyph proxy，但没有真实实例 mask 和文字像素分割 mask。
- 渲染排版：约 `45%` 接近 Koharu。已有 safeLayoutRect、字号回退、collision 诊断，但没有把真实 bubble ID mask 作为 renderer 主约束，也没有完整 CJK/竖排排版能力。
- 翻译质量：约 `20%` 接近 Koharu 实测效果。当前 Gemma 270M clean text pass rate 只有 `0.4545`，主流程 13 块只通过 1 块；这不是几何算法能单独补齐的。

如果把“达到用户实测 Koharu 那种竖写日语也能识别、翻译、排版”的效果作为 100%，AITRANS 当前更像是 `35%~45%`：诊断框架已成型，主算法和真实 artifact 还缺一半以上。

## Koharu 源码确认的真实链路

Koharu 不是“整页 OCR + 合并”。源码里 `Artifact` 是 pipeline 的依赖货币，engine 通过 `needs` / `produces` 声明输入输出，DAG resolver 决定执行顺序。

关键 artifact：

- `SourceImage`
- `TextBoxes`
- `SegmentMask`
- `BubbleMask`
- `OcrText`
- `FontPredictions`
- `Translations`
- `RenderedSprites`
- `FinalRender`

关键源码事实：

1. `artifacts.rs` 里 `TextBoxes`、`SegmentMask`、`BubbleMask`、`OcrText`、`Translations`、`RenderedSprites`、`FinalRender` 都是 readiness 判断的一等 artifact。
2. `engine.rs` 的 `EngineInfo` 声明 `needs` 和 `produces`，`build_order` 用 artifact producer 关系拓扑排序。
3. `pp_doclayout.rs` 产生真实 `TextBoxes`，过滤 text/title/content 类区域，去重，按高宽比判断竖排。
4. `ctd_full.rs` 同时产生 `TextBoxes` 和 `SegmentMask`。
5. `ctd_segment.rs` 在已有 TextBoxes 上跑 segmentation-only，并用 TextBoxes 约束 mask。
6. `postprocess.rs` 的 `refine_segmentation_mask` 明确没有 TextBoxes 时清空 mask；有 TextBoxes 时只保留扩张框内且超过阈值的文字像素，膨胀后再裁回框内。
7. `bubble_segmentation.rs` 产生真实 `BubbleMask`，每个气泡写成独立灰度 ID，不是 bbox。
8. `paddle_ocr.rs` 在每个 TextBox crop 上 OCR，而不是扫整页。
9. `llm_translate.rs` 收集 text node，批量翻译并写回每个 node 的 translation。
10. `renderer.rs` 和 `latin.rs` 使用 `BubbleIndex`：统计 seed bbox 下的多数 bubble ID，按真实 bubble mask 做 distance transform，求 safe rect，再用 rendered sprite 的非透明像素做 mask collision 检查。

这些源码点解释了为什么 Koharu 能处理竖写日语：它不仅 OCR 强，还先检测文字方向和文字框，OCR crop 可按 line polygon/方向校正，renderer 也有 `WritingMode::VerticalRl` 和 CJK/标点布局处理。AITRANS 目前只有 0/90/180/270 整页 OCR 和局部 shadow deskew，没有同等级 line polygon 与竖排主路径。

## 阶段差距矩阵

| 阶段 | Koharu 源码能力 | AITRANS 当前能力 | 差距判断 |
| --- | --- | --- | --- |
| DAG / 调度 | 真实 `Artifact` + `EngineInfo.needs/produces` + topo order | v1.31 起有 resolver/report-only DAG，主执行仍是 Swift store 顺序调用 | 框架概念接近，执行层未迁移 |
| TextBoxes | detector 先产出文字框，OCR 后置 | Vision OCR observations + bubble-first 融合 + TextBox proxy ledger | 最大缺口之一，仍用 OCR 反推结构 |
| SegmentMask | CTD / segmentation-only 产出文字像素 mask，并受 TextBoxes 约束 | glyph mask / SegmentMask proxy，传统阈值和连通域 | proxy 有价值，但不是模型级 mask |
| BubbleMask | speech-bubble-segmentation 输出实例 ID mask | 近白连通域、rounded-rect proxy、BubbleMask report | 缺真实实例 mask，安全区和 sibling 分割不可靠 |
| OCR 输入 | 只对 TextBox crop OCR，支持 line polygon / warp / 方向 padding | whole-page Vision + bubble-first + crop shadow，0 adopted | OCR 质量仍受整页 Vision 和 crop 护栏限制 |
| 长图 | detector slice 后还原坐标并去重 | 有 synthetic slice OCR 和长图机制，但 `test/1.png` 不触发 | 思路接近，真实 detector 缺失 |
| 竖写 | TextDirection、line polygon、VerticalRl renderer | 0/90/180/270 OCR，缺竖排 TextBox 主路径 | 距 Koharu 实测竖写能力差距大 |
| 翻译 | text nodes 批量翻译，模型/提供商更强 | Gemma 270M，逐块为主；batch tagged 曾格式崩坏 | 模型地板明显不足 |
| 清字 | SegmentMask + BubbleMask + inpainting / fill | glyph fill / background median proxy，主覆盖仍偏保守 | 未到真实清字 |
| 渲染 | BubbleIndex safe rect + sprite collision + vertical/CJK layout | safeLayoutRect、字号回退、render lock、RenderSprite fit planner report-only | 诊断接近，真实 renderer 约束不足 |

## 已经接近 Koharu 的部分

1. 主流程已从单一路径变成 `whole-page OCR + bubble-first` 融合，并有 post-fusion cleanup。相比 v5-v9，块级结构更稳定。
2. ground-truth-free 决策边界基本守住：融合、cleanup、crop gate、report gate 都避免用真值做生产选择。
3. 输出报告已经能定位 TextBoxes、BubbleMask、SegmentMask、Translation、Render 的 first blocking stage。
4. BubbleIndex、DistanceField、seam、RenderSprite fit 的概念已经进入 Swift 报告模型，后续接真实 mask 时有落点。
5. 外部 Koharu artifact 契约已定义，知道 active 目录必须交付 `1.manifest.json`、`1.textboxes.json`、`1.bubbles.json`、`1.segment_mask.json`。

## 仍然差很远的部分

1. 缺真实 TextBoxes detector。Koharu 的 OCR 不是定位器；AITRANS 现在仍依赖 Vision observation 先识别再合并，根上不同。
2. 缺真实 BubbleMask 实例 ID。rounded-rect / 近白连通域能做诊断，但遇到相邻气泡、尾巴、凹形气泡、跨面板时会失真。
3. 缺真实 SegmentMask。当前 glyph proxy 能避免部分粗暴覆盖，但不能像 CTD mask 那样稳定约束清字和 OCR。
4. 缺 line polygon / 局部 warp / 竖排方向主路径。用户提到 Koharu 竖写日语效果好，这正是 AITRANS 当前短板。
5. 翻译模型地板太低。clean text 只有 `0.4545`，说明即使 OCR 真值输入，当前模型也经常不达标。
6. v1.22-v1.38 多数工作是 report-only ledger，不能等同于真实能力闭环。

## 下一步优化方向

### P0：停止继续堆 report-only 层，转向真实 artifact 输入

下一步最该做的是让 `test/koharu_artifacts/` 得到真实 TextBoxes / BubbleMask / SegmentMask，然后先 shadow OCR，再评估收益。

验收目标：

- `externalArtifactReadinessReport.readinessVerdict = readyForShadowOCR`
- `externalTextBoxShadowOCRReport.executed = true`
- external TextBox crop 的 OCR 结果进入 `1_ocr_probe_text.txt`
- 仍不替换主流程，先证明哪些块能改善。

原因：v17-v20 已证明继续在内部 crop / line / deskew 参数上试参收益有限，且没有候选能 promoted。

### P1：实现 native TextBoxes detector-lite，而不是继续 OCR observation 聚类

如果短期拿不到真实 Koharu artifact，可以在 iOS 侧做一个 detector-lite：

- 从 bubble candidates 内部做文本候选区域，而不是整页 Vision observation 反推。
- 结合高对比连通域、stroke 密度、行投影、候选面积和方向判断。
- 输出真正的 `TextBoxCandidate` 列表，作为 OCR crop 的上游输入。
- 每个候选带 `sourceDirection = horizontal/vertical/unknown`。

关键要求：这层必须先生成 TextBoxes，再让 OCR 对 crop 工作，不能仍然叫 TextBoxes 但来源是 OCR 结果。

### P2：先做竖排日语专项 shadow path

为了向 Koharu 的竖写能力靠拢，建议新增竖排专项 shadow：

- 从 bbox 高宽比、字符排列、连通域列投影判断 `verticalCandidate`。
- 对竖排候选生成窄列 crop。
- 尝试局部旋转 / warp 后送 Vision OCR。
- 报告 `verticalOCRCandidateText`、`sourceDirection`、`rotationUsed`、`word/character preservation`。
- 不改主流程，先用日语竖排样例做评估。

这比继续针对当前英文横排 `test/1.png` 调参数更能贴近用户实测 Koharu 优势。

### P3：把 BubbleMask proxy 升级为真实 mask source

真实 BubbleMask 的最低目标不是完美分割，而是让每个气泡有 ID mask：

- 背景为 0。
- 每个气泡为 1...N。
- TextBox 用 bbox 下多数 ID 归属。
- safe rect 从 mask distance field 算，不从 rounded rect 算。
- 相邻气泡/同气泡 sibling 先 shadow，不直接影响主渲染。

只有这一步完成，v1.35-v1.38 的 BubbleIndex、DistanceField、seam、RenderSprite fit ledger 才能从“影子账本”变成可晋级算法。

### P4：翻译模型独立升级或对照

不要把 OCR 几何优化和模型质量混在一起判断。当前 clean text pass rate 已经证明 Gemma 270M 不是质量基准。

建议：

- 保留 Gemma 270M 做加载/闪退/接口冒烟。
- 增加 Qwen2.5-0.5B q4_k_m 或同级小模型对照，但不替换默认模型，先做 diagnostic model floor comparison。
- 对漫画块翻译重新做 tagged batch，但先用能遵守 tag 的模型验证，不再用已知格式崩坏的 Gemma 270M 推主流程。

### P5：渲染从 report-only 变成真实离屏 sprite gate

AITRANS 当前有 render collision 字段，但还没有 Koharu 那样把真实 bubble mask 作为 sprite 非透明像素约束。

后续晋级条件：

- 真实 BubbleMask ready。
- 每块译文先离屏渲染为 alpha sprite。
- 检查非透明像素是否全在所属 bubble ID 内。
- 失败时缩字号/重排/换行。
- 只在这套 gate 稳定后替换 overlay 布局。

## 推荐版本路线

1. `v1.39-real-koharu-artifact-shadow`：只接真实 `test/koharu_artifacts/` 并跑 external TextBoxes shadow OCR，不动主流程。
2. `v1.40-vertical-japanese-shadow`：新增竖排日语 shadow probe，验证 Koharu 优势场景。
3. `v1.41-native-textbox-detector-lite`：做 OCR 前 TextBox detector-lite，输出独立候选。
4. `v1.42-real-bubblemask-shadow`：从真实或 detector-lite mask 进入 BubbleIndex / DistanceField shadow。
5. `v1.43-model-floor-comparison`：引入更强小模型对照，确认翻译地板。
6. `v1.44-promotion-gate`：只有 TextBoxes / BubbleMask / SegmentMask / model floor 至少两项有实测收益后，再讨论替换主流程。

## 关键风险

- 不能把 v1.22-v1.38 的 Koharu 命名报告误认为真实 Koharu 算法已接入。
- 不能用 ground truth 手写 artifact 或理想 bbox 冒充 detector 输出。
- 不能继续在当前英文横排 `test/1.png` 上无限调 crop 参数，v20 已经显示这条线收益不足。
- 不能忽略模型地板。OCR 修好后，Gemma 270M 仍可能让最终效果差。
- 不能只看 `totalBlocksDetected` 或 `groundTruthMatchedBlocks`，需要看 OCR 文本、翻译通过率、render containment 和人工视觉效果。

## 最短回答：还差多少

从“工程架构理解 Koharu”看，AITRANS 已经走过一大半；从“真实用户效果接近 Koharu”看，还差一半以上。最该补的不是更多报告，而是真实 TextBoxes、真实 BubbleMask、真实 SegmentMask、竖排 crop/方向处理和更强翻译模型。当前最佳下一步是拿真实 Koharu artifact 或实现 native detector-lite，让 OCR 从“整页扫描”转成“结构化文字框 crop”，这是向 Koharu 靠近的分水岭。
