# Codex 任务 v4：修正可信准确率 + 自检数字一致性 + 干净文本诊断

上一轮跑出的 `ocrSimilarity` 和框架对比里的 `accuracyVsGroundTruth`（0.8378 / 0.8755）经过逐条核对，发现**不可信**，原因不是某一个简单的 bug，是几个问题叠加的。这一轮不是去"调高"这两个数字，是要先让这个数字本身变得站得住，再决定下一步怎么走。请按顺序处理，每改一处就重新跑一次探针，不要攒到最后一次性验证。

---

## 0. 背景：已经确认的具体问题

逐条核对 v3 跑出的 12 个块的明细数据后发现：

1. **参考真值清单本身不全**，导致至少 4 个块（编号 #6、#7、#9、#11）被"就近匹配"逻辑强行配上了完全不相关的真值文本，算出来的相似度分数是在比较两句毫不相干的话，没有意义。
2. **相似度算法对词序错乱过于宽容**。有几个块（#3、#8、#10）原文词序被打乱、专有名词丢失或损坏，依然拿到了 0.7~0.83 这种偏高的分数，但这几个块的翻译结果全部失败——分数和"这段文本是否还能被正常理解/翻译"明显脱节。
3. **候选选择逻辑有 bug**：#0 这个块，`afterPreprocessing`（预处理增强后的识别结果）实际上比 `rawOCR`（原始识别结果）更接近真值，但最终送进翻译的 `finalForTranslation` 却选用了更差的 `rawOCR` 版本，说明候选选择逻辑没有按预期工作。
4. **专有名词"Senpai's"在三个不同的块里被识别成三种不同的错误形式**（"REN-"、"SENPArS"、"SENPAIS"），不是偶然的单次错误，值得单独追踪。
5. 上一轮"双框架对比"里 `blocksFoundByBoth=8`、整图 12 块、气泡优先 15 块，但 `blocksOnlyInWholePage` 和 `blocksOnlyInBubbleFirst` 都是空列表——12-8=4、15-8=7，这两个数字不可能同时是 0，说明"匹配计数"和"列表填充"用了两套不一致的逻辑，这个矛盾也要一并修。


另外，画面里有一处装饰性标题文字"City Battler Offline Tournament 開催!!"，这种风格化标题文字和普通对话框气泡的识别难度不是一个量级，请在真值清单里**单独标记**这一类条目（比如加一个 `type: "decorative"` 字段，区别于普通对话的 `type: "dialogue"`），后续统计核心对话准确率时，这类条目不要混进同一个平均值里拉低或拉高整体数字。

核对完成后，请明确告诉我：现在的真值清单总共有多少条，是否已经完整覆盖图上所有可识别文字区域，还有没有遗漏的。

## 2. 匹配逻辑必须能"拒绝匹配"，不能强行配一个错误答案

这是本轮最关键的修复。现在的"就近匹配"逻辑，在找不到合适真值的时候，会默认选一个相似度最高（哪怕仍然很低）的真值条目强行配上去，导致 #6/#7/#9/#11 这种风马牛不相及的比较。

请改成：

- 设置一个**最低匹配置信度阈值**（具体数值你定，建议先用一个比较保守的值，比如要求达到某个相似度水平才采信这次匹配，阈值多少合适你可以通过对比 12 个块的实际情况来调）。
- 如果某个块和所有真值条目的最佳匹配相似度都低于这个阈值，**不要强行配上去**，而是标记为 `groundTruthMatch: "unmatched"`，并把这个块排除在准确率统计之外（但仍然要在报告里列出来，说明"未找到可信匹配"，不能直接消失不见）。
- 报告里需要新增一个统计：总共多少块"成功匹配真值"、多少块"未找到可信匹配"。如果"未找到可信匹配"的数量偏高，这本身就是一个值得关注的信号（可能是真值清单还不全，也可能是这块 OCR 结果已经烂到完全认不出原句），不要把这个信息隐藏掉。

修好这个逻辑之后，重新跑一次，对比哪些块从"被强行配错"变成了"正确匹配"或者"诚实标记为未匹配"，把这个变化在总结里列出来。

## 3. 重新设计相似度算法：必须对词序敏感

现在用的相似度算法（不管具体是什么实现）对词序错乱、单词丢失、重复伪影这几类问题过于宽容。请：

- 换成一个对词序变化敏感的算法，比如基于词级别的编辑距离（Levenshtein，允许插入/删除/替换，按词为单位而不是按字符，归一化到 0~1），而不是现在这种对词序不敏感的序列匹配方式。具体选哪种算法你可以自己决定并说明理由，但必须满足：词序被打乱的文本，分数应该明显低于词序正常但有少量字符错误的文本。
- 除了总相似度分数，**单独增加一个"词序是否正常"的信号**（不需要复杂算法，比如简单检查匹配上的词在原句和识别结果里的相对顺序是否一致），写入报告，不要把这个信息混进总分里看不出来。
- 用 v3 那 12 个块的真实数据（修正匹配之后的）重新算一遍，把旧分数和新分数并排列出来，对比差异，确认新算法确实能把 #3/#8/#10 这种"词序打乱但旧分数偏高"的块打到更低的分数。

## 4. 修复候选选择逻辑的 bug（注意：不能用真值做选择依据）

#0 这个块暴露的问题是：明明 `afterPreprocessing` 更接近真值，最终却没被选用。**但修复这个 bug 时要特别注意一点**：真实使用场景下（用户拍真实漫画截图），系统是没有真值可以比对的，所以"选哪个候选送去翻译"这个决策逻辑，**不能**改成"和真值比对，选更接近真值的那个"——这种做法只在我们有真值的测试环境里好看，对真实产品毫无用处，等于做了个假修复。

请先确认现在候选选择逻辑本来设计的依据是什么（比如应该是基于 Vision 给出的识别置信度、或者基于某种文本质量规则、或者别的标准），如果这个依据本身存在但没有被正确应用，修复让它生效；如果当时根本没设计任何依据、只是随便选了一个，需要重新设计一个**不依赖真值**的选择标准（比如：优先选置信度更高的候选；或者几个候选投票取交集更多的版本），并在测试环境里用真值数据**验证**这个标准选出来的结果是否确实更接近真值（验证用，不是选择依据）。这两件事请在报告里分开说清楚：选择标准是什么、为什么不依赖真值；测试环境下验证效果如何。

## 5. 专有名词损坏单独追踪

"Senpai's" 这个词在不同块里被识别成三种不同的错误形式，这种"反复出现、规律性的特定词汇识别失败"值得单独记录。请在报告里加一个字段，统计本轮测试中反复出现识别错误的高频词（不需要复杂的算法，统计一下哪些真值里的词，在多个块的 OCR 结果里都没有被正确识别出来即可），这个信息可以用来后续考虑要不要把这类词加进自定义词表（上一轮已经集成的功能）。

## 6. 自检要求：任何汇总数字都必须从明细数组里实时算出来，并加一致性校验

这是为了避免重复上一轮"双框架对比"那种数字自相矛盾的问题（`12 - 8 = 4` 但列表却是空的）。请检查整个探针报告的代码，确认：

- 任何"汇总性的统计数字"（比如总数、通过率、平均分、双框架对比里的差集列表），都必须是**从最终的明细数组现场计算出来的**，不能是某个独立维护、可能和明细数组不同步的单独变量。
- 在生成报告的最后一步，加一个简单的一致性校验：比如双框架对比里，`blocksFoundByBoth + blocksOnlyInWholePage.count + blocksOnlyInBubbleFirst.count` 应该等于两边总数的并集大小，如果校验不通过，不要默默放过，要在报告里明确报错/打印警告，说明哪两个数字不一致。
- 同样的检查也适用于"控制台/txt 打印出来的摘要数字"和"`probe_report.json` 里的明细数据"——这两处展示的应该是同一份数据算出来的，不能是两套独立逻辑各算一遍。请确认现在是不是这种情况，如果不是，统一成一处计算、多处展示。

请实际跑一次双框架对比，确认这次 `blocksOnlyInWholePage`、`blocksOnlyInBubbleFirst`、`blocksFoundByBoth` 三个数字加起来能对上总数，不再出现矛盾。

## 7. 干净真值文本直送翻译模型的诊断实验

这是用来回答"翻译失败到底是 OCR 噪声的锅，还是翻译模型本身能力不够"这个问题的关键实验，要排除 OCR 这个变量。

- 找出本轮 OCR 结果里**确认无误、和真值几乎完全一致**的块（比如 v3 里的 #5，"LET'S / BATTLER!" 对应真值 "Let's Battle!"，差异只有一个字母），以及第 1 节新补的真值条目（这两句如果对照原图核实后发现 OCR 也识别得比较干净，可以一起加入）。
- 对这些"干净样本"，**跳过 OCR 这一步**，直接拿真值文本本身喂给当前配置的翻译流程（保持现有最简英译中 prompt 不变），记录翻译是否通过现有的质量判定标准。
- 这个实验单独出一份小报告（比如 `clean_text_diagnostic.json`），列出每个干净样本的真值文本、模型 rawOutput、是否通过判定。
- 如果这些**排除了 OCR 噪声**的干净样本依然大比例翻译失败（复读、占位、瞎编），这就是"翻译模型本身能力不足"的有力证据；如果干净样本能正常翻译通过，说明现在残留的 OCR 噪声依然是主要瓶颈，还有继续优化 OCR 的空间，不急着换模型。
