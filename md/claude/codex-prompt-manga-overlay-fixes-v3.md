## 0. 开始前必须先澄清的事（这件事很重要，不要跳过）

我们看到上一轮跑出来的结果里，识别块数量从 50+ 降到了 12 个，看起来"气泡检测"已经在起作用。但请你先确认一件事，并在开始改代码前告诉我结论：

**现在的"块"是怎么来的？是下面哪一种，还是两种都有？**

- (a) 纯粹是"对 Vision 识别出的多个文字行/观察结果，按空间位置做了合并去重"——这种做法本质上还是先对整张图跑 OCR，再对识别结果做后处理分组，**不涉及任何图像层面的"气泡区域检测"**。
- (b) 真的做了图像处理意义上的"气泡检测"——比如检测画面里近白色、被边框包围的连通区域（气泡的视觉形状），在跑 OCR 之前就先把这些区域框出来。

这两者是完全不同的技术路径，请如实确认现在是哪一种，**不要因为效果变好了就默认认为已经做了 (b)**。如果现在做的是 (a)，那么第 5 节要求的"气泡检测"是一个全新的、需要从图像处理角度实现的功能，不是在现有合并逻辑上小修小补。

## 1. 预处理增强模块（主要工作，可开关）

这是本轮的重点。目标：在文字送入 OCR 之前，做一组可独立开关的图像预处理步骤，提升识别质量。

### 1.1 需要实现的具体预处理步骤

请实现以下几项，每一项都做成独立可控的子开关（不是一个总开关，因为我们需要知道具体哪一步起作用）：

- **灰度转换**
- **对比度/亮度调整**（自动或基于直方图的简单自适应方式即可，不需要复杂算法）
- **自适应二值化**（adaptive thresholding，把文字从背景里"洗"出来，对有纹理/阴影背景的气泡尤其有用）
- **裁切放大**：对一个候选文字区域（无论这个区域是来自整图 OCR 的某个识别块，还是来自第 5 节的气泡检测结果），把该区域单独裁出来，放大 2~3 倍后再重新跑一次 OCR，而不是依赖整图缩放后的小字直接识别。
- **去噪/锐化**（轻量级即可，比如简单的 unsharp mask，不需要引入超分辨率模型）

这几步的应用顺序、具体参数你可以自己决定合理的默认值，但要做到：

- **每一步都能单独开关**，可以只开二值化不开放大，或者全部开/全部关，用于后续对比测试哪一步贡献最大。
- 这个模块应该是**通用的**，不要只服务于某一个框架——无论是整图 OCR 流程，还是第 6 节的气泡优先流程，都应该能调用同一套预处理模块。

### 1.2 总开关

在开发页/探针入口提供一个总开关："启用预处理增强"，开启后用上面配置好的子步骤组合跑一遍；关闭则保持原有直接识别的行为。

## 2. OCR 纠错后处理模块（次要工作，简化实现，可开关）

这部分按你说的"先简单实现"做，不需要复杂的纠错框架，但必须包含一个安全护栏，原因是我们查过这方面的研究：LLM 做 OCR 纠错容易在原文错误率较高、整段文字混乱时产生幻规——也就是模型会"自信地编造"一个看起来合理但其实是瞎猜的修正结果，而不是承认看不懂。这对一个翻译类产品是个真实的风险，所以护栏不能省。

### 2.1 简洁的纠错 prompt

用一个最简单的模板，不要写得很长很说明性，类似：

```
以下文本来自漫画对话框的 OCR 识别结果，可能包含字符识别错误。
如果存在明显的拼写或字符错误，请修正为最合理的英文原文；
如果无法确定，原样输出。不要添加任何解释或标点说明。

文本：{ocrText}
```

具体措辞你可以微调，但保持这个"简洁、单一指令、不画蛇添足"的风格，跟项目里现有"把以下翻译成中文："这种极简提示词的风格一致。

### 2.2 安全护栏（必须实现，不能省）

纠错结果如果满足以下任一条件，**直接拒绝这次纠错，保留原始 OCR 文本**，不能让模型的"猜测"替换掉原文：

- 修正后文本长度和原文长度差异超过一定比例（比如 ±30%，具体阈值你定）。
- 修正后文本的词数和原文词数差异过大。
- 修正后文本里出现了原文里完全没有任何相似片段的全新词（比如原文是几个字符乱码，修正结果却凭空多出一整句没有依据的内容）。

被拒绝的纠错，要在探针报告里记录"纠错被拒绝，原因是 XXX，保留原文"，不能静默地什么都不显示。

### 2.3 总开关

同样在探针入口提供"启用 OCR 纠错后处理"开关。

## 3. 探针：两个增强模块的前后对比展示（这是本轮探针最重要的部分）

`probe_report.json` 的每个文字块，现在需要能看到完整的处理链路，而不是只有最终结果：

```json
{
  "blockIndex": 0,
  "rawOcrText": "原始 OCR 识别结果（任何增强都没开时的结果）",
  "preprocessingEnabled": true,
  "afterPreprocessingOcrText": "开启预处理增强后重新识别的结果（如果开关关闭则为 null）",
  "correctionEnabled": true,
  "afterCorrectionText": "纠错后处理的结果（如果被护栏拒绝，这里应该等于 afterPreprocessingOcrText 或 rawOcrText，并在 correctionRejectedReason 字段写明原因）",
  "correctionRejectedReason": "字符串或 null",
  "finalTextUsedForTranslation": "实际送进翻译的文本",
  "translatedText": "..."
}
```

具体字段名你可以按实际实现调整，但必须能让人一眼看出"原始识别是什么、预处理增强改了什么、纠错后处理改了什么、最后用了哪个版本"，这四层信息不能合并成一个看不出中间过程的最终结果。

报告顶部要记录这次运行启用了哪些开关（预处理的哪几个子步骤开了、纠错后处理开没开），方便对比不同开关组合的效果。

## 4. 集成 Apple Vision 新能力

### 4.1 `RecognizeTextRequest`（iOS 18+ 的 Swift 原生 API）

苹果在 iOS 18 / macOS 15 之后提供了一套新的 Swift 原生文字识别 API（`RecognizeTextRequest`，区别于旧的 `VNRecognizeTextRequest` + `VNImageRequestHandler` 组合），基于 async/await，结构更简洁。请：

- 先确认当前项目的最低部署目标（deployment target）是多少。如果低于 iOS 18，需要用 `@available` 做条件判断，新 API 只在 iOS 18+ 设备上启用，旧设备继续走现有的 `VNRecognizeTextRequest` 路径作为兼容回退。
- 在探针里加一项对比：同一张测试图，分别用旧 API 和新 API（如果当前开发/测试用的模拟器系统版本支持）跑一次，把两者识别到的文字内容差异记录下来——这两套 API 背后大概率是同一个识别引擎换了接口，但既然能测，就实际跑一次确认一下，不要假设结果完全一样。

### 4.2 自定义词表（custom lexicon）

Vision 的文字识别请求支持传入自定义词表，配合语言校正使用，对模型本来不熟悉的专有词汇/术语有针对性帮助。请：

- 在识别请求里加上自定义词表支持，词表内容先做成可配置的字符串数组参数。
- 针对 `test/1.png` 这张测试图，可以预置几个测试用词（比如这张图里出现的专有名词类词汇，你识别的时候应该能看到大概有哪些反复出现的特殊词，自己判断填哪些进去做验证，不需要我指定全部内容）。
- 探针里加一项对比：同一识别请求，词表开 vs 关，记录哪些文字块的识别结果发生了变化。
- 如实记录这个功能对"常见单词被认错"（比如 FEW 被认成 PEN 这种）大概帮助有限——自定义词表主要解决"词库里没见过的词"，不是解决"常见词被认错"，探针对比出来的结果如果验证了这一点，直接如实写进 README，不用为了让这个功能"显得有用"而夸大效果。

## 5. 气泡检测优化与量化（复用第 1 节的预处理模块）

先回到第 0 节的澄清结果。如果现在确认还没有真正意义上的图像层面气泡检测，这一节就是新增这个能力；如果已经有了，这一节是继续优化它。

### 5.1 气泡区域检测

实现一个基于图像处理的气泡区域检测：在原图上找近白色、被边框/轮廓包围的连通区域，作为候选气泡。具体算法你自己定（连通域分析、轮廓检测都可以），不需要追求完美，能找到大部分典型矩形/椭圆形对话气泡即可。

### 5.2 流程

对每个检测到的气泡区域：裁切出来 → 套用第 1 节的预处理增强（放大、二值化等）→ 在这个裁切后的子图上跑 OCR，而不是在整图上跑。

### 5.3 量化对比（必须有具体数字，不能只是"看起来更准了"）

这一步需要一份**人工核对过的参考真值**才能量化，不然没法说"准确率提升了多少"。我根据之前看到的截图，整理了一份这张测试图大致应该识别出的对话框文本草稿，但这是我从压缩过的截图里目测整理的，**不一定完全准确**，建议你或者我们其中一方对照 `test/1.png` 原图人工核对一遍再定稿，作为本次测试专用的参考真值文件（比如存成 `test/1.ground_truth.json`，明确标注这只是测试用，不进 App 正式逻辑）：

```json
[
  "I've arrived at Senpai's house.",
  "That's right, right now I'm—",
  "The City Battler Tournament starts in a few days.",
  "And that's why we're doing this special training.",
  "Even though I said it's just special training and asked if we could just play online—",
  "Or at least, that seems to be Senpai's logic.",
  "The suggestion was overruled, and it was decided that I'd be staying over at Senpai's house.",
  "Let's Battle!"
]
```

（"City Battler Offline Tournament 開催!!" 这种带日文混排的装饰性标题文字，识别难度本来就更高，可以单独标记，不强制要求和上面几句一样的准确率标准。）

有了参考真值之后，对每个气泡，计算"裁切放大二值化后识别结果"和"直接在原图上识别该区域"两者分别与参考真值的字符级编辑距离或词匹配率，得出一个具体的准确率提升数字（哪怕只是字符级相似度百分比这种简单指标），写进 `probe_report.json`，不要只下"明显更准"这种没有数字支撑的结论。

## 6. 双框架对比：整图 OCR（现状）vs 气泡优先 OCR（新），**不互相替代**

这点很重要，明确写在这里：**第 5 节新增的"气泡优先"识别路径，本轮只是新增一套独立的对比/测试路径，不能替换现有的整图 OCR 流程，也不能成为 Pro 翻译功能实际使用的默认路径**。现有整图 OCR（前几轮已经验证效果不错）继续作为主流程不变。

### 6.1 原因

整图 OCR 的优势是召回率有保障——只要文字在图上，理论上都有机会被识别到。气泡优先路径依赖"先把气泡框对"，如果气泡检测漏掉了某个不规则形状的气泡、或者某段文字根本不在一个标准气泡形状里（比如旁白框、特效字），这段文字可能直接被跳过，根本进不到 OCR 这一步。所以两套路径应该是互相验证、对比数据的关系，不是新的替代旧的。

### 6.2 探针要求

同一张 `test/1.png`，分别跑：

- **整图 OCR 路径**（现有流程，含之前已经做好的旋转合并/去重逻辑）
- **气泡优先路径**（第 5 节新增）

记录到 `probe_report.json` 里，至少包含：

```json
{
  "frameworkComparison": {
    "wholePage": {
      "totalBlocksDetected": 数字,
      "processingTimeMs": 数字,
      "accuracyVsGroundTruth": 数字或百分比
    },
    "bubbleFirst": {
      "totalBlocksDetected": 数字,
      "processingTimeMs": 数字,
      "accuracyVsGroundTruth": 数字或百分比
    },
    "blocksOnlyInWholePage": ["..."],
    "blocksOnlyInBubbleFirst": ["..."],
    "blocksFoundByBoth": 数字
  }
}
```

`blocksOnlyInWholePage` 用来验证我们的担心是不是真实存在——如果这个列表不为空，说明气泡检测确实漏掉了整图 OCR 能找到的内容，这是支持"两套路径长期并存、互相兜底"这个判断的实际证据，不是凭空猜测。

### 6.3 后续方向（这次不用实现，只是告诉你背景）

如果气泡优先路径的准确率明显更高，未来可以考虑做成一个用户可选的"高精度模式"或者 Pro Max 一类的付费分层功能，让用户自己选"更快但可能不够准的整图模式"还是"更慢但更准的气泡模式"。这次不需要做任何分层/订阅相关的代码，只需要把对比数据跑出来，给后续决策提供依据。
