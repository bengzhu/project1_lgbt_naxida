## 1. 本次目标

用项目根 `test/1.png`（一张英文对话的手机漫画截图，气泡分布在图片各处，文字可能是常规横排，也可能是漫画里常见的旋转/倾斜/弯曲艺术字效果）跑通一条完整链路：

```
test/1.png
  → Apple Vision OCR 识别文字块（含位置）
    → 当前已配置的本地 LLM 翻译每个文字块（英译中）
      → 在原文字块位置覆盖底色，绘制译文，盖住原文
        → 输出合成后的图片
          → 同步输出一份探针报告，逐项验证链路每一步是否正常
```

本次只做图片这一条链路，**不涉及音频**，不要动现有的 `test/` 音频识别相关代码（除非是必要的、不影响其行为的共用代码整理）。

## 2. 功能需求详细说明

### 2.1 输入

- 复用现有 `test/` 目录扫描逻辑里"找图片"的那部分（`.png/.jpg/.jpeg/.heic`），但本次新功能只需要处理 `test/1.png` 这张测试图，不需要支持目录下多张图片批量跑（如果现有扫描逻辑天然支持多张也无妨，但探针报告至少要清楚跑的是哪一张）。

### 2.2 OCR 识别（核心难点：尽量覆盖漫画里各种文字朝向）

- 使用 Apple Vision 的 `VNRecognizeTextRequest`，识别等级选 `.accurate`，`recognitionLanguages` 设为英文（源图是英文对话），可以开启语言校正。
- **关于"竖直排列"的处理方式，请注意一个重要前提**：Vision 框架内建的竖排文字支持，主要针对的是 CJK（中日韩）传统竖排阅读顺序，**不是**用来处理"英文字母被旋转/倾斜摆放"这种漫画拟声词/艺术字效果。所以不要指望靠 Vision 的某个"竖排开关"解决这个问题。
- 实际可行的做法：**对同一张图做多角度识别**（至少 0°、90°、180°、270° 四个角度，旋转图片后分别跑一次 OCR），把每个角度识别出的文字块结果，按照"还原回原图坐标系"后做去重/合并（同一块文字可能在多个角度都被部分识别到，取置信度更高或文本更完整的那次结果）。这样可以覆盖横排、竖排、倾斜等各种气泡文字朝向，而不依赖 Vision 对竖排的专门支持。
- 对每个最终保留的文字块，记录：原始识别文本、bbox（换算成图片像素坐标系，并说明你用的坐标系约定，比如左上角原点还是左下角原点）、使用的识别角度、Vision 给出的置信度（如果 API 提供）。
- 过滤掉明显无意义的识别结果（比如空字符串、单个无意义符号），但不要做过度清洗——这是探针测试，宁可多保留可疑结果让后续判定环节去标记失败，也不要在 OCR 阶段就悄悄丢弃，避免和现有项目"raw 探针不清洗不隐藏"的原则冲突。

### 2.3 翻译（复用现有本地 LLM 调用，不要新建一套翻译逻辑）

- 对每个文字块的识别文本，调用当前已经配置好的翻译流程（无论当前是 Mock 还是 Local 引擎，都应该正常工作；探针报告里需要写明本次运行时实际用的是哪个引擎）。
- 复用现有"英译中"方向的提示词逻辑，不要为这个新功能单独写一套 prompt 模板。
- 沿用项目里已有的翻译质量判定逻辑（参考现有"运行接口自测"对"返回原文"、"输出包含原文"、"输出不像目标语言"的判定方式），本次每个文字块的翻译结果也要套用同样的判定标准，写进探针报告。

### 2.4 覆盖合成（在原图上盖住原文、贴上译文）

对每个文字块：

1. **背景遮盖**：取该文字块 bbox，适当扩大一点边距（比如各方向扩大 10%~15%，确保覆盖到原文字的笔画边缘、斜体倾斜部分、描边阴影），用一个接近气泡背景色的颜色填充这个区域，盖住原文。
   - 背景色的取色策略你可以自行决定（比如采样 bbox 边缘环带像素的主色，或简单情况下退化为白色填充+浅色描边），但要保证"原文被盖住、译文清晰可读"这个结果优先于颜色取样的精细程度——这一步先求能跑通、效果可接受，不强求完美还原气泡底色。
2. **译文绘制**：在遮盖后的区域内绘制对应的中文译文，字号根据区域大小自动调整（让文字能在区域内完整换行排布，必要时允许略微突破原 bbox 但不要超出整张图片边界），颜色选择保证和底色有足够对比度，确保人眼能看清。
3. 所有文字块处理完后，导出为一张完整的合成图片。

### 2.5 输出文件

本次输出固定为以下几类文件（具体放在哪个目录，见第 4 节关于沙盒限制的讨论，这里先说清楚要产出什么）：

- `1_debug_boxes.png`：原图基础上，只画出所有识别到的文字块 bbox 框线（不做翻译覆盖），方便人工核对"框有没有框对地方"，这是因为覆盖合成之后人工反而不容易判断框线对不对，所以单独留一份调试图。
- `1_translated_overlay.png`：完整的覆盖翻译合成图。
- `probe_report.json`：结构化探针报告，见第 3.2 节。

### 3.2 探针报告内容（`probe_report.json`）

至少包含：

```json
{
  "sourceImage": "test/1.png",
  "engineUsed": "Local 或 Mock，写实际跑的引擎",
  "totalBlocksDetected": 数字,
  "blocks": [
    {
      "index": 0,
      "bbox": [x, y, width, height],

      "ocrText": "识别到的原文",
      "ocrConfidence": 数字或null,
      "translatedText": "译文",
      "checks": {
        "ocrNotEmpty": true/false,
        "translationNotEmpty": true/false,
        "translationNotEqualOriginal": true/false,
        "translationNotContainOriginal": true/false,

    }
  ],
  "overallPassed": true/false,
  "outputFiles": {
    "debugBoxesImage": "路径",
    "overlayImage": "路径"
  },
  "warnings": ["比如：检测到 0 个文字块、某个块翻译判定失败等"]
```

- 如果识别到 0 个文字块，或者所有块翻译判定都失败，`overallPassed` 必须为 `false`，并在 `warnings` 里写清楚原因——这种情况不算"运行报错"，但也绝对不能被当成"链路正常"。

### 3.3 判定标准总结

链路被判定为"正常跑通"，至少需要满足：

- 成功读取 `test/1.png`。
- OCR 识别到至少 1 个非空文字块（如果实际识别到 0 个，这不是探针的 bug，而是需要诚实报告"本次识别失败"，不要为了让测试"通过"而放宽判定）。

- 成功生成 `1_debug_boxes.png` 和 `1_translated_overlay.png` 两个文件，且文件非空。
- 成功生成 `probe_report.json`，结构符合上面的约定。

### 3.4 调试辅助

- `1_debug_boxes.png` 是这次任务里唯一能让人工判断"框选位置对不对"的依据，请确保框线足够明显（比如用醒目颜色、适当线宽），并在框旁边标注 `index` 数字，方便对照 `probe_report.json` 里的 `blocks[index]`。

## 4. 关于输出路径的现实限制（需要你判断并实现，不是开放讨论）

这是一个真实的技术限制，请按下面的方式处理，不要忽略：

iOS App 运行时是沙盒环境，**不能在运行时直接写入开发机上的项目根目录**（也就是 Xcode 项目文件夹本身），这一点不管是真机还是模拟器都一样，App 代码层面没有这个权限。但因为本项目目前的构建命令固定跑在 `generic/platform=iOS Simulator` 上，模拟器的 App 容器本身就是 Mac 文件系统里的一个真实文件夹（在 `~/Library/Developer/CoreSimulator/...` 路径下），所以有现实可行的办法：

- **App 内部**：把 `1_debug_boxes.png`、`1_translated_overlay.png`、`probe_report.json` 写到 App 自己的沙盒目录（建议跟现有 `state.json` 一样放在 `Application Support/AITRANS/` 下面新建一个 `Output/` 子目录，不要污染现有的会话/历史数据结构）。
- **导出到项目根 `output/`**：在 App 沙盒之外、用一段可以从命令行单独运行的脚本（shell 脚本即可，不需要做成 App 功能），在模拟器跑完一次测试后，找到当前运行中模拟器的这个 App 容器路径（可以用 `xcrun simctl get_app_container <device> <bundle id> data` 拿到沙盒根路径），把 `Output/` 目录下的文件复制到项目根新建的 `output/` 文件夹。把这个脚本一并写出来（比如 `scripts/export-probe-output.sh`），并在 README 里写清楚怎么用。

请不要为了"图省事"而尝试让 App 在 DEBUG 模式下用硬编码的开发机绝对路径直接写项目根目录——这种写法即使在模拟器上能跑，也会把开发机路径硬编码进 App 代码里，污染代码库，而且换一台开发机或者换用户就直接失效，不是一个干净的方案。用"沙盒内输出 + 外部脚本导出"这两步分离的方式更稳妥。
