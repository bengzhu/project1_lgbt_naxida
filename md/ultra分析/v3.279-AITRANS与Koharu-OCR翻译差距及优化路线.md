# AITRANS v3.279 与 Koharu OCR、日语竖排识别、翻译与成品链路差距分析

> 日期：2026-08-13
> AITRANS 基线：`smalldata_test` / `5a2287e16f35e01741c5e31b0356727b82132875` / v3.279 receipt
> Koharu 基线：仓库内 `reference/koharu-main` 当前快照
> 范围：代码与已有证据的静态审计，本轮未本地编译、未运行 Core ML / Xcode / Rust / App runtime，未使用子智能体。

## 1. 结论先行

AITRANS 与 Koharu 的差距已经不是“有没有竖排 crop”。v3.260-v3.279 已经把一大段 Koharu MIT48 路径的几何和组块语义迁入 AITRANS，包括 RGB→luma、nearest 预处理、Triangle detector resize、竖排 rotate270、projective bilinear line warp、TextRegion owner、行覆盖证明、owner-first grouping 和完整 block fallback 替换边界。如果只看“MIT48 line crop 与 block ownership 逻辑”，AITRANS 已经进入后半程。

但是，用户真正感知的 OCR 和翻译效果仍与 Koharu 有大差距，核心原因是：

1. AITRANS 迁移的主要是 **Koharu 的输入几何与组块规则**，但实际输出文字的仍是 bundled Manga OCR，不是 MIT48，也不是 Koharu 当前默认的 PaddleOCR-VL。
2. AITRANS 有 RT-DETR 矩形文字区域和 Vision character geometry，但没有 Koharu 主链的原生 `TextRegion + line_polygons + SegmentMask + BubbleMask`。上游候选质量仍是限制项。
3. AITRANS 的日语图片翻译已有 tagged batch、缺失块补译和逐块安全回退，但产品翻译只有 Mock / Local 两种引擎，内置质量底座是 Gemma 3 270M Q4。导入任意 GGUF 的文件接口存在，但 prompt 仍硬编码 Gemma `<start_of_turn>` 模板，还不是通用 GGUF 翻译适配层。
4. Koharu 的“翻译好”不只是 prompt 更好。它允许使用 1.2B/1.5B/7B/8B/14B/32B 翻译模型，也可以连接 OpenAI、Gemini、Claude、DeepSeek、OpenAI-compatible、DeepL、Google Translation 和 Caiyun。AITRANS 与这个模型/提供商上限的差距，远大于两者 tagged-block prompt 文案的差距。
5. 目前没有可以支撑“AITRANS 日语 OCR 准确率已经达到 Koharu 多少”的共享泛化评测。`test/jap.jpg` 的 7/7 是云端 Koharu MIT48 对七个固定 crop 的 oracle，不是 AITRANS 主链识别结果，也不能代表其它字体、斜排、网点、气泡和长页。

因此，当前最准确的判断是：

- **狭义 MIT48 crop / owner 逻辑迁移成熟度：约 75%-85%。**
- **端到端 OCR 流程逻辑成熟度：约 55%-65%。**
- **翻译编排逻辑成熟度：约 60%-70%，但模型/提供商产品能力只约 15%-25%。**
- **包含清字、inpainting、竖排 shaping 和成品渲染的完整漫画翻译链路：约 35%-45%。**
- **实际质量可信度：低，当前只能估为 20%-35% 的“已证明能力覆盖”，不是准确率。**

上述百分比是按代码入口、语义对齐、产品主路实际可用性和证据广度得出的工程区间，不是 CER、BLEU、COMET 或人工评测分数。

## 3. 双方当前端到端链路

### 3.1 AITRANS v3.279 图片日语主路

```text
图片数据
  -> Vision 整页 OCR
  -> Vision 90° / 270° 日语方向侦察
  -> bundled RT-DETR 文字区域检测（长页分片）
  -> bundled Manga OCR 对 detector bbox / strict line quad crop 识别
  -> Vision vertical block / line / perspective / axis / pixel-first / tile fallback
  -> confidence + Japanese script density + geometry + owner gates
  -> owner-aware 去重、行覆盖、block fallback 替换
  -> ImageOCRLayoutEngine 竖排归组、右到左漫画阅读顺序
  -> ImageTranslationBlock[]
  -> 每批最多 8 blocks / 1800 chars 的 tagged 日语图片翻译
  -> 缺 tag 逐块补译，格式失败整批逐块回退
  -> 复查、修正、单块重识别/重译、方向覆盖、忽略/恢复
  -> 矩形底色覆盖 + UIKit 水平文字/逐字竖排绘制
```

核心入口：

- `AITRANS/Services/VisionOCRService.swift:124-249`：日语 OCR 总编排。
- `AITRANS/Services/ComicTextBubbleDetectorService.swift:61-132`：640 输入、CPU-only RT-DETR、长页分片、输出 rect + confidence。
- `AITRANS/Services/MangaOCRService.swift:928-1367`：Core ML Manga OCR encoder/decoder、greedy decode、confidence、Koharu-compatible luma / nearest 预处理。
- `AITRANS/Services/ImageOCRLayoutEngine.swift:88-790`：方向、owner、行/块归组和阅读顺序。
- `AITRANS/Services/TranslationSessionStore.swift:1251-1383`：图片 OCR→翻译→覆盖导出主流程。
- `AITRANS/Services/TranslationSessionStore.swift:4631-4770`：tagged batch、缺失块补译和逐块回退。
- `AITRANS/Services/TranslationSessionStore.swift:26811-26992`：矩形 overlay 与逐字竖排导出。

### 3.2 Koharu 当前默认主路

Koharu 当前 `PipelineConfig::default()` 不是 MIT48 主路，而是：

```text
SourceImage
  -> PP-DocLayoutV3                    => TextBoxes / TextRegion
  -> YuzuMarker font detector          => FontPredictions
  -> Comic Text Detector segmenter     => SegmentMask
  -> Speech Bubble Segmentation        => BubbleMask (instance ID mask)
  -> PaddleOCR-VL engine               => OcrText
  -> selected local/remote translator  => Translations
  -> LaMa Manga                        => Inpainted
  -> Koharu Renderer                   => RenderedSprites + FinalRender
```

Koharu 同时提供 `manga-ocr` 和 `mit48px-ocr` 作为可替换 OCR engine。其关键不只是模型多，而是每个 engine 声明 `needs` / `produces`，通过 artifact DAG 连接：

- `TextBoxes`
- `SegmentMask`
- `BubbleMask`
- `OcrText`
- `FontPredictions`
- `Translations`
- `Inpainted`
- `RenderedSprites`
- `FinalRender`

这使检测、OCR、清字、翻译和渲染之间的中间产物可持久、可替换、可审计，不需要让 OCR observation 同时承担检测、方向、所有权和布局全部职责。

## 4. OCR 差距详析

### 4.1 已经明显对齐的部分

AITRANS 的以下能力已经不是表面模仿，而是进入产品日语 OCR 主路：

- detector 输入规范化为 DeviceRGB，并使用 image-rs 等价 Triangle resize。
- Manga OCR 使用 image-rs 整数 luma 公式和 nearest floor coordinate mapping。
- detector bbox 仍是 ownership 主边界，strict quad 只在弱 bbox 识别后作 fallback。
- 竖排 line quad 使用 bounded target canvas、projective mapping、floor 四邻域 bilinear 和 rotate270。
- 日语结果有 confidence `>= 0.55` 与 Japanese script density `>= 0.5` 门槛。
- 长页 detector slicing、请求上限、候选上限和 pixel budget 都是有界的。
- v3.276-v3.279 已经对齐 `block_index` 所有权、owner-first grouping、exact-owner line coverage 与完整 fallback 替换 partial lines 的边界。
- 最终布局支持竖排列自上而下、列间自右向左，并避免不同 known owner 相互吸附。

这部分的主要剩余风险是组合状态数量大，而不是关键语义仍完全缺失。

### 4.2 最大缺口一：OCR 模型没有迁移

AITRANS 的 `MangaOCRRuntime` 加载：

- `MangaOCREncoderINT8`
- `MangaOCRDecoderINT8`
- 可选 batch encoder / decoder
- `MangaOCRVocab.txt`

这是 Koharu 可选 `manga-ocr` engine 的 Core ML 路径，不是 `Mit48pxModel`。MIT48 的模型结构、字典、可变宽 48px 输入、confidence 和颜色预测都没有进入 AITRANS target。

所以当前实际做的是：

```text
Koharu MIT48 的 crop / line / grouping 方法
                    +
AITRANS bundled Manga OCR 的识别表征与 decoder
```

这个组合可以减少方向错误、截断和重复，但不会自动获得 MIT48 对小字、漫画字体和竖排行的模型能力。对同一个理想 crop，两个 OCR 模型仍可能给出完全不同的文字。

更重要的是，Koharu 当前默认 OCR engine 已经是 `paddle-ocr-vl-1.6`，其实现使用 PaddleOCR-VL 模型包对每个 TextBox crop 做 multimodal OCR。因此，后续不能把“继续复制 MIT48 crop 规则”当成完整 Koharu OCR 迁移。

### 4.3 最大缺口二：上游 TextRegion 结构还是近似值

AITRANS detector 的产品输出结构只有：

```swift
rect: ImageOCRLayoutRect
confidence: Float
```

它没有直接产出：

- native line polygons
- 持久化 TextRegion ID
- per-line detector score
- bubble instance ID mask
- segment mask
- OCR engine provenance
- text / stroke color prediction

AITRANS 当前使用 Vision character boxes、已有 OCR observations 和几何规则重建 line candidates。这些候选经过严格门控，但本质上仍是“用识别结果反推检测结构”。Koharu 的设计是先有 detector / layout TextRegion，OCR 只负责读字。

这个差距会在下列场景放大：

- OCR 先错，导致 character geometry 也不完整。
- 断裂笔画、浅色文字或网点背景使 Vision 不给 character box。
- 斜排、弧形、不规则 SFX 不能用简单竖排列表示。
- 两个邻近 TextRegion 在宽 bbox 内共存。
- 小型 kana / punctuation 被当作孤立噪声。

### 4.4 最大缺口三：没有可比较的多引擎 OCR 框架

Koharu 将 OCR 视为可替换 engine，AITRANS 则在 `VisionOCRService` 内把 Vision、detector、Manga OCR 和大量 fallback 组成一个日语特例。当前并不能轻松回答：

- 某块是 Manga OCR 读出还是 Vision 读出？
- 是 bbox、quad、line 还是 block fallback 获胜？
- 新 OCR engine 在同一 crop 上比旧引擎好多少？
- 不同引擎的 confidence 如何校准？
- 用户手动修正是哪个候选的反例？

`ImageTranslationBlock` 主要持久化文本、翻译、confidence、bbox 和方向，不持久化 OCR engine / crop provenance 和候选列表。这是下一阶段做可审计 A/B 的结构性缺口。

### 4.5 当前规则的边际收益已经下降

v3.260-v3.279 已连续处理了预处理像素级差异、crop envelope、line quad、方向 provenance、owner、coverage 和 fallback 重复。这些都是正确修复，但如果继续只围绕 `test/jap.jpg` 新增特殊规则，将出现三个问题：

- 固定样图过拟合，未知页面不获益甚至回归。
- `VisionOCRService.swift` 已超过 4,400 行，候选组合和去重边界的状态空间持续扩张。
- 上游 detector 或 OCR 模型给不出正确信号时，下游几何无法凭空恢复真实文字。

后续应把“新规则默认开启”改为“共享语料证明收益后才晋级”。

## 5. 翻译差距详析

### 5.1 翻译编排逻辑已经接近，不是当前最大矛盾

AITRANS 日语图片路径已经具备：

- 按 OCR 最终阅读顺序生成 `[N]` blocks。
- 每批最多 8 块 / 1800 字符，避免小模型上下文失控。
- 要求保留 tag，禁止合并、拆分、遗漏和重排。
- 解析已成功部分，对缺失 tag 逐块补译。
- batch 格式失败时整批逐块回退。
- 单块重译、取消、失败恢复和已有译文保留。

Koharu 的本地翻译也是 tagged blocks + professional manga translator system prompt + parser。两者在“不让块数和顺序失控”这一层的思路已经接近。

### 5.2 最大缺口一：Gemma 270M 是接口冒烟模型，不是翻译质量基准

AITRANS 内置模型是：

```text
Gemma 3 270M IT QAT Q4_0
241,410,624 bytes
```

仓库 README 和 AGENTS 已经明确将它定义为加载、接口和闪退冒烟，不是翻译质量基准。历史 clean-text 英译中 `5/11` 与下列错误一致：

- 译文继续保留大段英文。
- 直接返回原文。
- 中英混杂，关键词未翻。
- 格式说明、项目符号或占位回答。
- tagged batch 遗漏、新增或错排 tag。

调整 temperature、继续添加“只输出译文”或扩展清洗规则，不能把 270M 的语言能力变成专用 7B 漫画翻译模型的水平。

### 5.3 最大缺口二：“可导入 GGUF”不等于“正确支持任意 GGUF”

`GemmaLocalService.translationPrompts` 对所有导入模型都生成 Gemma 风格：

```text
<start_of_turn>user
...
<end_of_turn>
<start_of_turn>model
```

`LlamaRuntime` 直接 tokenize 这个字符串，没有读取 GGUF chat template 并根据 Qwen、Llama、Sakura、Hunyuan 等模型渲染消息。因此：

- Gemma 格式模型是主支持路径。
- 其它 GGUF 可能被加载，但不保证 prompt template 正确。
- 将 Qwen/Sakura 文件替换为 `model.gguf` 不是完整模型迁移。

Koharu 的 `PromptRenderer` 会使用模型 chat template，并对 VNTL、Hunyuan 等模型有特定消息格式。这是 AITRANS 要支持更强本地模型时必须先补的适配层。

### 5.4 最大缺口三：模型与提供商选择空间

AITRANS 产品引擎枚举只有：

```swift
case mock
case local
```

Koharu 则同时具备：

- 专用本地漫画翻译模型。
- 多档体积/质量本地 GGUF。
- OpenAI / Gemini / Claude / DeepSeek / OpenAI-compatible。
- DeepL / Google Cloud Translation / Caiyun。
- 模型专用 prompt rendering 和可自定义 system prompt。

因此“AITRANS 的日语翻译逻辑比 Koharu 差多少”要分两层回答：

- tagged 块编排与失败回退逻辑：差距已不大。
- 真正决定译文的模型、模板适配和 provider 上限：差距很大。

### 5.5 语境与一致性仍不足

AITRANS 日语图片主路把最终 blocks 分成最多 8 块的小批。这比逐块翻译更好，但仍缺少：

- 跨 batch 的人名、称呼、性别和口癖一致性。
- 项目/作品级术语表与译名记忆。
- 当前块的前后句上下文，但又不允许模型改写非目标块。
- 拟声词、旁白、对话、标题的不同翻译策略。
- 译文长度与气泡可用空间的反馈。
- 翻译后的数字、人名、标点、未译日文和 tag 完整性 QA。

Koharu 也不是完整文学翻译系统，但它的整页 text nodes 批量翻译、更强模型和自定义 prompt 给了更高的上限。

## 6. BubbleMask、SegmentMask、清字与渲染差距

这一部分不直接提高 OCR 文字准确率，但决定“翻译完的图像像不像成品”。

### 6.1 AITRANS 当前产品路径

- `ImageTranslationBlock` 不包含 BubbleMask、SegmentMask、font prediction 或 stroke color。
- PNG 导出在原图上填充黑色/青色矩形，然后绘制白色翻译文字。
- 竖排是按 Unicode vertical presentation forms 和逐字 cell 绘制，不是 HarfBuzz `vert` / `vrt2` shaping。
- 超出容量的竖排文字会截断并加 `…`。
- `MangaOverlayProbeService` 内有大量 bubble/segment/mask/safe-layout 影子账本，但这些不等于用户图片翻译主路已运行 native mask 模型。

### 6.2 Koharu 当前路径

- speech bubble segmenter 输出每个气泡独立 ID 的像素 mask。
- comic text segmenter 输出并用 TextRegions refine 的文字 mask。
- LaMa Manga 同时使用 SegmentMask、BubbleMask 和 TextBlocks 扩展清字区域并 inpaint。
- renderer 使用 inpainted 底图、bubble mask、font prediction、字形 shaping、字体 fallback、紧密 ink bounds 和像素碰撞检查。
- 竖排 CJK 是真正的 top-to-bottom shaping 和 right-to-left columns，不是逐字模拟。

这是完整成品链路中 AITRANS 最大的剩余差距，但它应与 OCR 准确率优化分开验收。

## 7. UI 与操作体验并不是单向落后

AITRANS 当前在移动端 OCR 复查上已有一组实用能力：

- 低置信与方向待定筛选。
- 局部原图预览和当前 block 定位。
- 修正 OCR 原文后只重译当前 block。
- 恢复 Vision OCR baseline。
- 忽略/恢复错误 block。
- 水平/竖排/自动方向覆盖。
- 单块重新识别、单块重译和 scoped cancel。
- 保留其它块、复查进度和已有译文。
- VoiceOver 操作、焦点回归和状态说明。

这些是 AITRANS 的实际优势，不应在迁移 Koharu 时被一个桌面编辑器 UI 直接覆盖。但要让复查真正帮助 OCR 迭代，仍缺少：

- 显示当前块来自哪个 OCR engine / crop variant。
- 在多个 OCR 候选中选择，而不是只看一个最终文本。
- 手动移动/缩放 bbox、拆分/合并 block、调整阅读顺序。
- 将用户修正以可匿名、可选择的方式记录为评测反例。
- 显示“OCR 错”、“方向错”、“组块错”、“翻译错”的不同重试入口。

## 8. “还差多少”的透明评分

### 8.1 评分方法

每个区间同时考虑四件事：

1. Koharu 语义是否已在 AITRANS 代码中实现。
2. 它是否真正进入用户主路，而不是 report-only / shadow probe。
3. 实际模型或 artifact 是否等价。
4. 是否有足够广的数据证明效果。

### 8.2 分项矩阵

| 能力 | 逻辑迁移成熟度 | 产品主路成熟度 | 证据信心 | 决定性剩余差距 |
| --- | ---: | ---: | --- | --- |
| TextRegion / detector | 55%-65% | 45%-55% | 中低 | 只有 rect + confidence，native line polygon / mask 缺失 |
| 竖排 crop / warp / rotate / preprocess | 75%-85% | 65%-75% | 中 | 主要语义已迁移，但候选来源不同 |
| OCR 模型与 decoder | 35%-45% | 30%-40% | 低 | 仅 bundled Manga OCR，无 MIT48 / PaddleOCR-VL 产品引擎 |
| owner / coverage / grouping / reading order | 75%-85% | 65%-75% | 中高 | owner 为临时上下文，上游不是 native TextRegion |
| OCR 质量 gate 与失败回退 | 70%-80% | 65%-75% | 中 | confidence 未跨引擎校准，缺共享 benchmark |
| tagged 翻译编排 | 60%-70% | 55%-65% | 中 | 小批、部分解析和回退已有，项目语境不足 |
| 翻译模型/提供商 | 15%-25% | 15%-25% | 中高 | 270M + Gemma 固定模板，无可比的 provider/catalog |
| BubbleMask / SegmentMask / inpainting | 25%-35% 研究覆盖 | 5%-15% | 高 | 大部分只在探针/契约，主路无 native model artifacts |
| 成品渲染 | 30%-40% | 25%-35% | 高 | 矩形 overlay + 逐字竖排，非 inpaint + shaping |
| OCR 复查 UX | 75%-85% | 75%-85% | 中高 | 缺 provenance、多候选和几何编辑 |

### 8.3 为什么用户感知差距会大于逻辑差距

端到端结果是串联系统：

```text
最终可用概率
≈ 检测覆盖
× crop/方向正确
× OCR 文字正确
× 阅读顺序正确
× 翻译充分
× 渲染可读
```

任何一层为零，后面再好也无法挽回。所以即使 AITRANS 已完成大部分 crop / owner 逻辑，只要 OCR 模型仍读错关键字，或 270M 仍返回原文，用户感知的结果仍是“很差”。

## 9. 后续优化路线

### P0：先把比较做成可信的工程系统

#### P0.1 建立共享日语 OCR 语料

`test/jap.jpg` 继续作为回归页，但不再作为唯一优化目标。建议首批语料至少包含：

- 20-30 张可合法用于测试的完整页。
- 150-300 个人工标注 TextRegion。
- 竖排对话、水平对话、斜排、旁白、SFX、小字、浅色字、网点背景、非白气泡、无气泡文字。
- hiragana / katakana / kanji / Latin / number / punctuation 混排。
- 字体、分辨率、压缩、旋转、长页和摄影透视变体。

标注至少包含：

- block polygon / bbox
- line polygons 或 line order
- writing direction
- exact source text
- block reading order
- bubble association（可见时）
- 文本类型：dialogue / narration / SFX / title / other

#### P0.2 建立分层指标

| 阶段 | 主指标 | 必须单独报告的失败 |
| --- | --- | --- |
| detector | recall / precision / F1 @ IoU 0.5，小区域 recall | 漏检、多检、跨块误并 |
| line geometry | line coverage、polygon validity、direction accuracy | 截字、反向、错行 |
| OCR | CER、block exact match、假名/汉字/标点 CER | 插入、删除、替换、空结果 |
| grouping | duplicate / omission rate，block exact composition | partial + fallback 重复、跨 owner 合并 |
| reading order | exact page order，Kendall tau | 列反向、水平/竖排交错 |
| translation | tag completeness，clean-input adequacy，MQM 人工错误 | 误译、漏译、未译、人名不一致 |
| end-to-end | 完整可用 block rate | 明确归因到 OCR / order / translation / render |
| performance | p50/p95 latency、peak memory、energy、峰值温度 | 按设备档位报告 |

Japanese script density 可以继续作为噪声 gate，但不能作为 OCR accuracy 代理指标。“全是日文字符”也可以每个字都错。

#### P0.3 在同一 crop 上跑引擎对照

对每个标注 crop 同时保留：

- AITRANS bundled Manga OCR
- Apple Vision
- Koharu MIT48 cloud-only oracle
- Koharu 当前默认 PaddleOCR-VL oracle
- 未来候选的可分发 OCR engine

必须分开评测：

1. **oracle crop OCR**：检查模型本身。
2. **detected crop OCR**：检查 detector + crop + OCR。
3. **full page output**：检查 grouping + order + fallback。

只有这样才能回答下一个错字到底应修 detector、warp 还是换 OCR 模型。

### P1（OCR）：将 OCR 从特例集收敛为可替换引擎

#### P1.1 新建 OCR engine 中间层

建议将下列概念从 `VisionOCRService` 的私有组合状态抽出：

```text
DetectedTextRegion
  id
  bbox
  polygon / linePolygons
  direction + confidence
  detector provenance + score
  optional bubbleID

OCRCandidate
  regionID / lineID
  engine
  crop variant
  text
  raw confidence
  calibrated confidence
  geometry
  owner
  rejection reasons
```

保留当前所有 bounded budgets 和 owner 规则，但让 Vision、Manga OCR 和新引擎在同一中间层上运行。

#### P1.2 先补 native line / TextRegion 信号，再继续细化 fallback

下一个高价值 OCR 改动应来自：

- 可分发的 line detector / text segmentation 输出。
- 从 detector 直接获得的 polygons，而不是 OCR 后反推。
- 将 detector region ID 传入 OCR、layout 和 review，不只在一次 recognition pass 内作临时 owner。

在这一层没有新证据前，不建议继续围绕一个固定 crop 添加第九、第十种方向 fallback。

#### P1.3 用数据选 OCR 模型，不先假定 MIT48 必须入 App

应以语料上的 CER / exact match / latency / memory / license 矩阵决策：

- 继续使用 Apache-compatible bundled Manga OCR。
- 换成或增加可分发的更强 OCR。
- 将大模型改成用户按需下载，而不是继续增大 App bundle。
- 保留 MIT48 为 cloud reference oracle。

MIT48 模型与 Koharu 源码快照均带 GPL 边界。在没有明确的产品授权与发布决策前，不应直接把 GPL runtime / weights 复制进 AITRANS target。“实现行为兼容”、“运行 GPL 工具做云端 oracle”与“在 App 中分发 GPL 代码/权重”必须继续保持不同边界。

### P1（翻译）：建立真正的翻译模型层

#### P1.4 先修模型模板适配，再对比更强 GGUF

必须先完成：

- 读取并应用 GGUF chat template。
- 模型级 prompt profile，支持 Gemma / Qwen / Llama / Sakura / Hunyuan 等格式。
- 模型能力 metadata：推荐语言对、上下文、内存档位、默认解码。
- 不支持的模型明确拒绝或标记 experimental，不再只因为“能加载”就称为可用。

然后在同一 clean-text 语料上比较：

- 当前 Gemma 270M（仅作 floor）
- 约 1B-2B 的移动端低内存档
- 约 7B 的高质量本地档
- 可选 remote provider 上限

应分别建立：

- 日语→简体中文
- 日语→英语
- 英语→简体中文（保留历史回归）

三套 clean-text 基准。

#### P1.5 页面上下文与术语一致性

在更强模型可用后，再增加：

- 整页有界 batch，必要时按 panel / bubble group 分批。
- 术语表、人名表、称呼策略和已确认译名。
- 上一批的只读摘要作为下一批 context，不允许模型返回额外 block。
- 对 SFX / narration / dialogue 使用不同长度和语气策略。
- 翻译后 QA：tag 完整、原文泄漏、数字/专名词一致、目标语言密度、过长译文。
- QA 不通过时只重译失败块，不重跑整页 OCR。

### P2（复查 UI）：将复查界面变成 OCR 迭代入口

#### P2.1 候选与 provenance

在复查页为每个 block 保留可展开的工程信息：

- final engine / crop variant
- detector confidence / OCR confidence（分开显示）
- 候选文本及差异高亮
- 为什么候选被采用/拒绝
- 方向和 owner / region 来源

默认 UI 仍保持简洁，只在低置信或开发者模式展开细节。

#### P2.2 几何编辑

按优先级增加：

1. 拖动/缩放当前 bbox，并只重识别该块。
2. 手动拆分 block。
3. 手动合并相邻 block。
4. 调整阅读顺序。
5. 恢复自动几何 baseline。

这些操作比继续增加隐式几何规则更能解决真实页面的长尾。

### P2（成品链）：最后补 native mask、清字和成品渲染

这一阶段必须独立于 OCR 评测，避免用“导出图更好看”冒充“OCR 更准”。

建议顺序：

1. 选定可分发的 SegmentMask 和 BubbleMask 模型。
2. 将 mask 变成图片会话主路的结构化 artifact。
3. 先做 mask 安全区和碰撞检查，不立即改原图。
4. 再引入可撤销、可单块重跑的 inpainting。
5. 将导出从矩形 overlay 升级为 inpainted base + shaped text sprite。
6. 对竖排 CJK 使用 CoreText vertical forms 或可控 shaping 引擎，验证 `vert` / `vrt2`、字体 fallback、标点、ink bounds 和 right-to-left columns。

## 11. 后续 Agent 执行指令

本节不是方向性愿望，而是下一位 Agent 可以直接执行的修改协议。若代码在后续版本中移动，应以符号名和职责为准，不要机械依赖本报告的行号。

### 11.1 不可跳过的通用协议

每轮开始前按以下顺序执行：

1. 切到并更新 `smalldata_test`，确认它与 `origin/smalldata_test` 的关系，再从该点创建唯一研发分支 `codex/v3.xxx-<topic>`。
2. 阅读根目录 `AGENTS.md`、本报告、最近一个已完成版本记录，以及本轮会碰到的 Koharu reference 源文件。不得只看交接摘要就修改代码。
3. 记录一个可证伪假设，例如“同 crop 的新 OCR 在 holdout 竖排小字 CER 上优于 bundled Manga OCR”，而不是“继续优化 OCR”。每个版本只验证一个主要假设。
4. 先保存基线 artifact，再写实现；评测集、指标定义和候选实现不能在看到结果后一起调到通过。
5. 本地严格禁止 `xcodebuild`、`xcrun`、`swift`、`swiftc`、Core ML/App runtime、Rust/Cargo 和任何会间接调用它们的 runtime shell。执行历史 Python contract 前先静态检查是否存在 `subprocess`、`os.system`、`Popen` 等进程入口；存在则留给云端。
6. 后续不使用子智能体。`main` 只展示不改；`smalldata_test` 是主开发分支；本地和远端合计只保留 `main`、`smalldata_test` 与至多一个研发分支。
7. 研发分支产生实现候选 SHA 后，才触发带 `expected_commit_sha` 的 exact-SHA cloud full。旧 run 被新 push supersede 后不得继续引用旧 artifact。
8. 云端实现、benchmark、Xcode/JUnit/UI 和 receipt 全部满足本轮门槛后，再开 PR 合入 `smalldata_test`；检查合入后 push CI，写 receipt，删除研发分支。不得触碰 `main`。

每轮必须保持以下实验纪律：

- `test/jap.jpg` 是必要回归页，但不能单独让候选晋级。
- ground truth 只能进入离线 scorer，不能被 App 的候选选择器、fallback 或阈值读取。
- 同一版本不要同时更换 detector、OCR 模型、翻译模型和 renderer，否则结果无法归因。
- 没有 holdout 改善时应记录负结果并停止该方向，不得为了版本号把 shadow 候选强行升为产品主路。
- 用户修正不得默认上传或变成遥测；若未来收集反例，必须另做明确的同意、匿名化和删除策略。

### 11.2 v3.280：先建立 benchmark，不改产品输出

v3.280 的唯一目标是让“AITRANS 与 Koharu 到底差多少”开始可以重复计分。该版本不得改变 OCR 候选、候选胜负、请求预算、翻译 prompt、UI 或渲染。

建议新增以下仓库级文件；名称可按现有规范微调，但职责不能混合：

```text
benchmarks/japanese_ocr/README.md
benchmarks/japanese_ocr/schema/fixture-manifest.schema.json
benchmarks/japanese_ocr/schema/prediction.schema.json
benchmarks/japanese_ocr/schema/report.schema.json
benchmarks/japanese_ocr/fixtures/manifest.json
benchmarks/japanese_ocr/examples/minimal/...
benchmarks/japanese_translation/schema/fixture-manifest.schema.json
benchmarks/japanese_translation/examples/minimal/...
scripts/evaluate-japanese-ocr-benchmark.py
scripts/evaluate-japanese-translation-benchmark.py
scripts/test-v3280-japanese-benchmark-contract.py
```

不要把新语料直接放进 `test/`：当前 Xcode 工程把整个 `test` folder reference 作为 App resource，继续往里塞完整页会无意增加 App bundle。`test/jap.jpg` 保持历史兼容；新 benchmark 放在未加入 app target 的顶层 `benchmarks/`，新增 Swift 文件时则必须显式更新当前手工维护的 `AITRANS.xcodeproj/project.pbxproj`。

OCR fixture manifest 至少必须声明：

- schema version、dataset version、split（train/dev/holdout）和整份 manifest SHA。
- 每张图的相对路径、SHA-256、像素尺寸、来源、许可证、允许的用途和标注者状态。
- 稳定 `pageID` / `regionID`，统一为左上原点的 normalized polygon / bbox，并拒绝越界、自交和退化 geometry。
- exact source text 原值及 NFC 规范化值；不能默认丢标点、空格、长音号或全半角差异。
- writing direction、region reading order、可选 line polygons / line order、text type 和测试标签。
- `test/jap.jpg` 必须标记为 legacy regression；七个 MIT48 crop 不能伪装成整页人工 ground truth。

prediction schema 至少必须声明：

- exact app SHA、dataset SHA、engine ID/version、模型/权重 SHA、license、设备和运行参数。
- 运行层级：`oracleCrop`、`detectedCrop` 或 `fullPage`，三者禁止混算。
- 每个预测的 region/line ID、原始文字、confidence、bbox/polygon、reading order、engine 和 crop variant。
- failure / empty prediction 也必须显式记录，不能从 JSON 中消失。
- cloud-only oracle 必须带 `referenceOnly: true`，不得被报告为 App bundled capability。

指标计算器必须使用结构化 JSON 解析和确定性算法，并至少输出：

- Unicode 原值 exact match 与 NFC exact match。
- CER 及 substitution / insertion / deletion 分解；空预测按删除计，额外预测按插入/false positive 计。
- detector precision / recall / F1 @ IoU 0.5；区域匹配使用确定性一对一最大匹配，不能用会随输入顺序变化的简单 greedy。
- duplicate、omission、block composition、direction accuracy、exact page order 和 matched IDs 上的 Kendall tau。
- vertical / horizontal / SFX / small text / long page 等分层的 micro 与 macro 结果，不能只输出总平均。
- schema、图片 SHA 或 dataset SHA 不一致时 fail closed，不生成“看似成功”的分数。

翻译 benchmark 必须将 clean source 与 OCR-corrupted source 分为两套输入。自动硬门只负责 tag completeness、missing/extra/duplicate/order、原文泄漏、目标语言密度和长度；accuracy、fluency、角色语气、术语与漏译需要盲评记录，不能用 BLEU 或脚本密度单独宣称翻译更好。

v3.280 允许修改 `.github/workflows/ci-results.yml`，但只能用于：验证 schema/fixture、运行纯 scorer、把 `japanese-ocr-benchmark-report.json`、`japanese-translation-benchmark-report.json` 和人类可读 summary 放入 CI artifact。它不得因此改变 App runtime。该版的合同至少覆盖 malformed geometry、SHA mismatch、重复 ID、缺失预测、空 GT、Unicode/标点、确定性重跑和 train/holdout 隔离。

v3.281 才开始建立 OCR 中间层，并先做 **shadow ledger + 零输出回归**。建议新建 `AITRANS/Models/ImageOCRProvenance.swift`，不要继续让已很大的 `TranscriptModels.swift` 和 `VisionOCRService.swift` 承担所有新类型。由于工程不是 file-system synchronized group，新文件必须加入 PBX file reference、Models group 和 Sources build phase。

```text
ImageOCRRegionID
ImageOCREngineID
ImageOCRCropVariant
ImageOCRCandidateRole
ImageOCRCandidateProvenance
ImageOCRCandidate
ImageOCRSelectionReason
```

`regionID` 是页面会话内稳定的 detector/TextRegion 身份；`verticalTextRegionOwner` 仍是当前 recognition pass 的临时 Koharu `block_index`。两者不能直接改名后混为一物。

| `ComicTextBubbleDetectorService.swift`：`ComicTextDetectorRegion`、`detectTextRegions` | 在最终 merge + deterministic sort 后分配页面内 region identity，并在 shadow report 中保留 detector source/score；若保留 slice 来源，必须说明 merge 后的聚合规则 | 不因添加 ID 改 NMS、merge、slice、阈值或输出顺序；不要假称 rect 已是 Koharu native line polygon |
| `ImageOCRLayoutEngine.swift`：`ImageOCRLayoutObservation`、`layout`、`cluster` | 接收并向最终选择结果传递 provenance；v3.281 的 layout 仍只依据当前 text/confidence/geometry/direction/boundary/owner 语义 | 不依据 engine 名称新加偏好，不重写 owner-first grouping、ownerless compatibility 或 manga reading order |
| `TranscriptModels.swift`：`ImageTranslationBlock` | 需要跨重启显示 provenance 时，只新增可选、版本化字段，并用旧 session fixture 验证 Codable 向后兼容；优先把类型定义放进独立模型文件 | 不把临时 owner、整套大候选图或 benchmark ground truth 写入持久 block；不破坏旧历史记录解码 |
| `TranslationSessionStore.swift`：图片 OCR 入块与基线恢复路径 | 维护 block ID 到 provenance/candidate ledger 的单一 source of truth；修正、恢复、单块重识别后明确哪个 ledger 失效或更新 | 不改变 scoped cancel、Vision baseline、reviewed IDs、失败 generation、其它译文和持久化时机 |

v3.281 应新增 `scripts/test-v3281-image-ocr-provenance-no-selection-change-contract.py` 和 cloud-only Swift evaluator。至少用固定输入证明：旧投影与新投影的最终 text、rect、direction、confidence、顺序完全一致；bbox/quad provenance 不丢；known owner 不跨块；旧 Codable fixture 可解码。只有这些成立，下一版才能用 ledger 做引擎对照。

### 11.4 OCR v3.282-v3.285 的逐版修改边界

| 版本 | 唯一主要假设 | 允许修改 | 本版禁止顺手修改 | 必须新增的证据 |
| --- | --- | --- | --- | --- |
| v3.282 | 同一 crop 的多引擎结果能分离 detector 与 recognizer 责任 | `benchmarks/`、cloud-only oracle scripts、workflow artifact 汇总；按 regionID 合并 Vision / bundled Manga / pinned MIT48 / pinned PaddleOCR-VL 结果 | 不改 App 候选选择，不把 GPL oracle 打包，不把不同 crop 层级混算 | oracle-crop 与 detected-crop 分表；每个 engine 的 revision/SHA/license/失败行；dataset SHA 固定 |
| v3.283 | 新的 native line/TextRegion 信号在共享语料提高 geometry recall | detector/line signal 的独立协议、`ComicTextBubbleDetectorService` 或新 service 的 shadow 输出、provenance ledger | 不让 shadow geometry进入产品胜负，不删除 Vision fallback，不先加新 OCR 模型 | detector/line recall、截字、跨块误并、duplicate/omission 和预算；holdout 上有收益才继续 |
| v3.284 | 某个可分发 OCR 候选在相同 crop 上有质量/资源优势 | 独立 OCR engine adapter、模型 manifest/下载或 bundle 策略、shadow inference、benchmark runner | 不默认启用，不更换翻译模型，不隐瞒模型尺寸/峰值内存/许可证 | CER/exact/latency/memory/energy/license 矩阵；至少一档真实目标设备的云端或受控设备证据 |
| v3.285 | 冻结的、与 GT 隔离的选择策略可安全晋级候选 | 小范围 product gate、feature flag/回退、candidate selection policy、Store provenance | 不在 holdout 结果出来后调阈值，不读取 fixture/GT，不扩大现有 page request/pixel budgets | train/dev 冻结策略后一次性 holdout；输出、重复、漏块、顺序、取消、内存均过门；旧引擎可立即回退 |

v3.282 的合并器必须按 `datasetSHA + pageID + regionID + cropLevel` 对齐，禁止按数组下标拼不同 engine 的结果。若新模型只改善 oracle crop、detected crop 不改善，下一步应修 detector/crop；若 detected crop 正确而 full page 仍重复，应修 fusion/layout；只有相同 crop 上文字仍错，才有证据把资源投入 recognizer。

v3.283 不预设必须复制 PP-DocLayoutV3 或 PaddleOCR-VL。先审查候选模型的许可证、权重来源、平台可运行性和资源预算；没有可分发 artifact 时，保持 cloud-only research，不创建伪“native”产品路径。

v3.285 的 production selector 只能读取运行时可获得的信息，例如 engine capability、crop role、校准后的质量信号和 geometry；不得读取文件名中的 benchmark 标签、人工文本或期望 region 数。不同 engine 的 raw confidence 不在同一尺度，未经 calibration 不能直接取最大值。

### 11.5 翻译适配修改地图

翻译方向应从 v3.286 开始，且先修模板兼容，再谈更强模型。仓库当前 `GemmaLocalService.translationPrompts` 为所有 GGUF 手写 Gemma `<start_of_turn>` / `<end_of_turn>`；`LlamaRuntime.generateLocked` 只 tokenize 已拼好的字符串。bundled `llama.xcframework` 已暴露以下 API，可以直接使用，不需要先升级 llama.cpp：

```text
llama_model_chat_template
llama_chat_apply_template
llama_chat_message
```

建议新建 `AITRANS/Models/LocalModelPromptProfile.swift` 或等价独立文件，表达 system/user messages、template source、known fallback profile、语言能力和默认 decoding，而不是继续向 `GemmaLocalService.swift` 填模型名 `if/else`。

v3.286 的具体改法：

1. `LlamaRuntime.swift` 新增“messages -> model chat template -> rendered prompt”的窄 API；正确管理 C string lifetime，先查询输出长度，再分配 buffer，并把负值/不支持模板作为显式错误。
2. 加载模型后读取内嵌 chat template；不要接受 `llama_chat_apply_template` 的隐式随机 ChatML fallback。template 缺失时，只允许用户明确选择的 known profile，未知模型应标记 experimental 或拒绝。
3. `GemmaLocalService.swift` 将翻译 instruction 与模型包装分离：现有 Gemma profile 的最终 prompt 和清洗行为先做到 byte-for-byte 或语义零回归，再增加 Qwen/Sakura 等 profile。
4. 保留 `generateMangaBlockTranslation` 的 tag parser、partial valid result、缺 tag 补译和失败处理；模板层不得吞掉 `[N]`。
5. `TranslationSessionStore.swift` 的 `imageTranslationBatches` 继续保持最多 8 blocks / 1800 chars，`parseMangaTaggedTranslations`、missing-offset 补译和逐块回退保持原语义。v3.286 不同时加入页面 context 或术语表。

v3.286 至少新增：

- `scripts/test-v3286-local-gguf-chat-template-contract.py`
- cloud-only template evaluator，覆盖 embedded Gemma、Qwen/Sakura fixture、缺模板 known fallback、未知模板拒绝、Unicode 和 buffer resize。
- 现有 Gemma prompt snapshot、tagged batch parser、deterministic/raw probe 回归。
- exact model filename、SHA、quantization、template 来源和 decoding profile 的 artifact 记录。

v3.287 只做同一 clean-text 语料上的多模型/量化对照，不立即更换默认模型。当前 270M 只能作为 floor。候选必须分别报告日译中、日译英、英译中，以及 p50/p95 latency、首 token、peak memory、context overflow 和热状态；若 7B 只在不现实的设备档位运行，应作为高质量可选档而不是默认档。

v3.288 才允许加入项目术语、人名/称呼记忆、跨 batch 只读摘要和 translation QA。上下文只能影响目标 block 的翻译，parser 仍拒绝 extra/duplicate/out-of-order tags；QA 失败只重译失败块，不重跑 OCR 或整页。新增合同应覆盖跨页泄漏、旧术语撤销、数字/专名保留、原文泄漏、超长译文、取消与部分成功持久化。

### 11.6 UI 与几何编辑修改地图

UI 建议放在 v3.289，且 provenance 展示和几何编辑分两个可回退的小步骤。`ImageTranslationViews.swift` 已经承担大量筛选、预览、修正、恢复和 VoiceOver 焦点逻辑；不要继续把所有新界面塞回同一个文件。建议新增独立 SwiftUI 类型，例如：

```text
AITRANS/Views/ImageOCRCandidateDisclosureView.swift
AITRANS/Views/ImageOCRGeometryEditor.swift
AITRANS/Views/ImageOCRReadingOrderEditor.swift
```

具体边界：

- 默认结果行仍显示最终 OCR 与译文；engine、crop variant、候选差异和拒绝原因只在低置信块或开发模式的 `DisclosureGroup` 展开，避免普通用户面对工程日志。
- 候选详情读取 Store 的只读 provenance；候选采用、bbox、split、merge、order 等业务 mutation 必须进入 `TranslationSessionStore` 的可测试方法，View 只保留 sheet、选择和焦点等局部 `@State`。
- bbox 编辑先提供拖动/缩放、取消和恢复自动 baseline，再只重识别该块；不要在拖动每一帧启动 OCR。提交后使用现有 scoped task identity 和 generation guard。
- split/merge/order 要定义 ID、已有译文、reviewed 状态、Vision baseline、provenance 和进行中任务如何迁移或失效，不能只改数组外观。
- 保留 v3.263-v3.274 已有 scoped cancel、失败恢复、筛选隐藏后的焦点回退、预览/结果行 focus origin、VoiceOver 状态和复查进度。
- 新按钮使用带文字语义的 system icon/`Label`，触控区域至少 44x44；支持 Dynamic Type，不依赖颜色区分候选，图像手势有等价的可访问控件和明确 accessibility label/value/hint。
- 大候选列表使用 lazy 容器；差异计算和候选排序不要放在频繁执行的 SwiftUI `body` 中。新增类型需加入 PBX project，并在 cloud full 开启 `ui_evidence_mode=full` 验证紧凑与大字号布局。

UI 的第一版不要同时实现 split、merge、排序和 mask 编辑。推荐先做“只读 provenance + 选择已有候选”，再做“单 bbox 编辑 + 恢复 baseline”，每一步都验证取消、焦点、筛选与持久化。

### 11.7 明确禁止顺手修改的边界

后续 Agent 在对应版本之外不要做以下事情：

- 不重写 v3.276-v3.279 的 owner assignment、owner-first grouping、exact-owner coverage 和完整 block fallback replacement。
- 不新增围绕 `test/jap.jpg` 的第九、第十种固定坐标 crop、方向或文字特判。
- 不把 GPL Koharu / MIT48 source、runtime 或 weights 打入 AITRANS target；cloud reference parity 与 App 分发继续隔离。
- 不把 `MangaOverlayProbeService` 的 proxy BubbleMask/SegmentMask 或 report-only ledger 接入产品后称为 native model output。
- 不让 benchmark ground truth、文件名、期望块数或人工更正参与生产候选选择。
- 不直接用不同 engine 的 raw confidence 排序，也不为了“平均分更高”把 detector confidence 与 OCR confidence 混成一个值。
- 不在 provenance 版本同时改变 OCR 阈值、请求预算、layout、翻译模型和 UI。
- 不在 chat-template 版本同时替换默认 GGUF、扩大 batch/context 或增加 remote provider。
- 不把完整 benchmark corpus 加入 App resource，不把所有新模型/候选/视图继续堆入 `TranscriptModels.swift`、`VisionOCRService.swift` 或 `ImageTranslationViews.swift`。
- 不用更好看的 overlay、固定 crop oracle 或脚本密度，替代 CER、翻译盲评或端到端 holdout 证据。

### 11.8 每版合同、云端与合并闭环

每个版本至少需要四层验证：

1. **静态边界合同**：Python 只检查 schema、source boundary、workflow route、版本和禁止依赖；不要让纯字符串合同成为唯一正确性证据。
2. **行为 evaluator**：Swift/Core ML/模型行为只在云端运行，覆盖正例、ownerless/foreign owner、empty/duplicate/malformed/cancel 等反例。
3. **benchmark artifact**：JSON 必须记录 exact candidate SHA、dataset SHA、engine/model SHA、配置、分层指标和失败明细；summary 只从该 JSON 生成。
4. **产品 full validation**：云端 Xcode、JUnit、UI/Home/Paste/Speech 与本轮相关 runtime 全部通过，receipt 发布成功。

本地允许的收尾只包括已确认无进程入口的静态 contract、Python AST、YAML/plist/shell 语法检查和 `git diff --check`。不要执行名称带 `runtime.sh` 的历史脚本；例如 v3.279 runtime 内部明确调用 `xcrun swiftc`，只能留给云端。

候选 push 后使用当前 workflow 的 exact-SHA guard，等价流程为：

```text
git rev-parse HEAD
gh workflow run ci-results.yml \
  --ref <唯一研发分支> \
  -f validation_profile=full \
  -f probe_mode=full \
  -f expected_commit_sha=<上一步 SHA>
```

若有实质 UI 改动，再加 `-f ui_evidence_mode=full`。Agent 必须确认 run 的 `headSha` 等于候选 SHA，下载并检查 benchmark JSON、manifest、JUnit、Xcode log 和 receipt；只看 GitHub 绿色图标不够。dataset 或实现一旦新 push，旧 run 自动作废。

PR 合入流程必须记录：实现候选 SHA、full run ID、PR run ID、merge SHA、合入后 push run ID、benchmark dataset SHA 和关键指标。合入后仅在证据真实成立时更新 `AGENTS.md` 版本摘要；随后同步本地 `smalldata_test` 并删除本地/远端研发分支。

### 11.9 后续 Agent 的决策表

| 观察到的结果 | 正确下一步 | 不应做什么 |
| --- | --- | --- |
| benchmark 无法稳定复跑或 dataset SHA 漂移 | 留在 v3.280 修 schema/scorer | 开始换 OCR 模型 |
| oracle crop OCR 好、detected crop 差 | 修 detector/crop/line geometry | 继续调 decoder 清洗 |
| detected crop 好、full page 重复或漏块 | 修 fusion/owner/layout，并添加对应反例 | 再加一个 OCR engine |
| 相同 oracle crop 上所有旧引擎都错，新引擎明显好 | 进入可分发性、资源和 shadow 评估 | 立即默认启用 |
| 新引擎 dev 提升但 holdout 回归 | 保持 shadow 或终止 | 用 holdout 调阈值后重报同一次结果 |
| chat template 修复 tag 格式但译文内容不提升 | 只声明兼容性提升，进入模型对照 | 声称日语翻译质量已超过 Koharu |
| clean-text 翻译好、OCR-corrupted 输入差 | 加 translation QA/上下文前先改善 OCR 或鲁棒性 | 把错误归因给 renderer |
| OCR/翻译都正确但成品不可读 | 独立进入 mask/inpainting/shaping benchmark | 回头用 OCR 指标包装视觉改进 |

每次交接最后必须留下：本轮假设、改动文件、未改边界、候选 SHA、dataset SHA、云端 run/receipt、关键分层指标、失败样例、剩余风险，以及下一轮唯一建议。缺少其中任何一项，下一位 Agent 应先补证据，不要继续堆功能。

## 12. 每一阶段的必要验收门

### OCR 晋级门

- 在共享语料报告 CER、exact match、detector recall、duplicate / omission、reading order。
- 分别报告竖排、水平、小字、SFX 和长页，不只报总平均。
- `test/jap.jpg` 继续回归，但不允许单独决定晋级。
- 任何新引擎都必须有 license、权重来源、SHA、体积、内存和设备运行表。
- 不将 confidence 直接跨引擎比较，先校准或只在引擎内比较。
- 不用 ground truth 参与产品候选选择。

### 翻译晋级门

- 先跑 clean source，再跑 OCR-corrupted source，两者必须分开。
- 日译中必须有独立基准，不使用英译中 `5/11` 代替。
- tag completeness / duplicate / missing / out-of-order 必须为硬门。
- 人工评测至少区分 accuracy、fluency、character voice、terminology、omission 和气泡长度。
- 报告实际模型名、量化、prompt template、解码参数和 provider，不只写“Local GGUF”。

### 工程与云端验收门

- 继续严格禁止本地 Xcode / Swift / Core ML / Rust 编译与 runtime。
- 本地只运行不启动外部进程的静态 contracts、AST/YAML/plist/shell 语法和 `git diff --check`。
- 任何产品实现候选都需 exact-SHA cloud full，云端 Xcode/JUnit/UI 与 OCR benchmark artifacts 同时通过。
- GPL Koharu / MIT48 仍只能在明确 cloud-only reference 边界运行，除非未来有新的授权与发布决策。
- `main` 继续只展示，`smalldata_test` 为主开发分支，同时最多保留一个研发分支。

## 13. 应立即停止的误优化方向

- 停止把固定 `test/jap.jpg` crop 通过当成通用日语 OCR 提升。
- 停止在没有共享语料前声称 CER、准确率或“超过 Koharu”。
- 停止将 MIT48 几何逻辑的迁移描述为 MIT48 模型迁移。
- 停止继续用 Gemma 270M 评估产品翻译上限。
- 停止把“可导入 GGUF”视为通用模型兼容，直到 chat template 适配完成。
- 停止把 `MangaOverlayProbeService` 的 proxy mask / report-only 账本写成产品主路 native masks。
- 停止用更好看的 overlay 或排版代替 OCR / translation 质量评测。
- 停止无上限扩展 Vision fallback 组合；每一条新路径都必须有数据上的独立增益。

## 14. 最终判断

AITRANS v3.279 已经成功学到了 Koharu 日语竖排 OCR 中一批最难写对的“工程语义”：像素预处理、方向、line warp、TextRegion owner、覆盖证明、组块和阅读顺序。这部分不应推倒重来。

但当前已经到了明显的分水岭：继续抄更多 crop / fallback 规则，无法替代真正的 OCR 模型、native TextRegion / masks、更强翻译模型和可比较评测。

后续优化的正确主线应调整为：

```text
共享语料与指标
  -> OCR engine / provenance 中间层
  -> native TextRegion / line 信号
  -> 同 crop 多引擎对照
  -> 按证据选择可分发 OCR
  -> GGUF chat-template 适配
  -> 更强日译中模型与页面语境
  -> provenance / 几何复查 UI
  -> native masks / inpainting / shaped renderer
```

简化成一句话：**AITRANS 已经学会了 Koharu 怎么把竖排文字送进 OCR，但还没有拿到 Koharu 同级别的“眼睛”和“翻译大脑”，也还没有完整的清字与排版链。**
